## Summary (the recommendation in nine lines)

1. **One home for the learner: a hub.** One always-on machine (default: `carson`, the desktop) holds each vault on its local disk: `state.sqlite`, the authored YAML and Markdown, and the content-addressed originals store. Every surface is a client of that one copy: the desktop app at the hub, the phone (PWA and Shortcut over Serve), the laptop (browser first, a remote mode of the desktop app later), and chat (MCP over Funnel). SQLite is never shared across machines and never file-synced (§6).
2. **A headless primary on the hub.** A `learnloop hub serve` user service holds the vault's *primary role* (an OS lock) and runs the background duties the desktop app runs today (ingest runner, post-attempt diagnosis, maintenance). It discovers work that any process queued from the moment it starts, so dailies done on the phone, the laptop or in chat are graded, diagnosed and planned while the desktop app is closed. The desktop app beside it attaches as a secondary and submits its ingest and Reader work as durable jobs the primary runs. Without the service (a contributor's machine), the desktop app is primary exactly as today (§6.2).
3. **Data leaves the code repository.** The owner's working vaults move to a private data root on the hub (default `~/learnloop-vaults/<name>/`), copied with the backup API (the configured database path resolved first) and verified before anything is removed. Textbooks move to a private books folder; after import LearnLoop only ever reads its own store copy (§6.3, §7.1).
4. **Sources never depend on a path again.** The originals store is the authority for every revision's bytes; `canonical_uri` and `original_uri` become provenance only. This completes the E1 fix that `fix/reread-safety` starts, and adds content-hash identity for local files so a moved book is the same book (§6.4).
5. **The code repository becomes clone-and-test clean.** No personal data the owner has not chosen to publish, no tracked database, no third-party file without a verified redistribution licence, no git-LFS. Test vaults are generated from text by builders; the migration-head fixture becomes a SQL text dump built at session start; real-vault checks become an opt-in lane run on backup copies (§7.2, §7.3).
6. **Backups are part of the move, not an afterthought.** Hourly backup-API snapshots that are complete by construction (every original they reference is in them), each copied off the hub's disk the same hour to an encrypted restic repository, a monthly restore drill, and honest labels: doctor and Settings show the age of the newest complete copy on another device, which is what a dead disk would cost (normally under an hour). If an hour is too much, the interval shortens (down to 15 minutes). A restore uses only a whole snapshot, whose database and files were taken at one quiesced point and are checked against one manifest, so it never pairs a database with files from another moment; continuous replication of the database alone (Litestream) is deferred (§6.7, §11).
7. **Offline is stated, not implied.** Away from home the laptop and phone reach the hub over the tailnet whenever both have internet. With no hub reachable: capture queues (phone and laptop browser outboxes), practice waits (mobile D9 holds). A read-only laptop snapshot and offline practice with deferred grading are deferred with triggers (§6.6, §11).
8. **The repository stays public; personal data and non-redistributable files leave its tip when the owner triggers S0.** It is public, has a public fork, and today serves the owner's databases, extracted book text and copyrighted PDFs to anonymous requests (§3.3). S0 removes from the tip every database holding the owner's learning history and every third-party file without a verified redistribution licence. The owner has deferred it (2026-10-14): it starts on the owner's trigger, after the current round of big implementation stages has landed and once the owner has copies outside the checkout, and until then the tip keeps serving what §3.3 lists. S1 meanwhile moves the live vaults out of the checkout, so no new learning history enters the repository. `migration_head_202`, which 21 test files need, is sanitized by whichever of S0 and S3 lands first: its video transcript and the owner's six answers are replaced with project-authored text, and if the owner does not approve what remains, it leaves too, its tests waiting in the owner lane for S3 (or, if S3 runs the sanitization, it is rebuilt synthetically at once; §7.2). Only small samples whose licences permit redistribution stay (§3.5). Old commits keep serving them until the owner settles history (H1 recommended, §7.4); forks and clones keep their copies under every option. History is the owner's action alone (D1, D2).
9. **Opt-in data contribution is designed for, not built.** A future n>1 model needs a versioned, redacted, pseudonymous, consented export of learning traces under a data licence, kept in a dataset store separate from the code repository. §6.12 fixes the constraints that keep it possible without retrofits; the build (S9) waits for its triggers (§11).

## 0. Thesis

LearnLoop is local-first by design: one learner, one vault, SQLite with append-only evidence, YAML for authored knowledge, and a replay that rebuilds every derived table. That design is sound on one machine. It was stretched to several machines through git: the owner's working vaults and their `state.sqlite` files live under `fixtures/` in the code repository, and textbooks live in git-LFS beside them. Git is a good way to share code and a poor way to share a live database. It merges text, not B-trees; it cannot carry a `-wal` safely; it makes every contributor download the owner's history; and on a public repository it publishes that history.

The tailnet already gives what git was standing in for. Every device the owner uses can reach one machine over WireGuard, from home or away, and the mobile and chat frontends already run as second processes beside the desktop app against one vault (`docs/specs/spec_mobile_tailnet_v1.md` §3.3; `docs/specs/spec_mcp_frontend_c1.md` §3.3 on `mcp/c1-read-context`). The design that keeps every invariant is to stop copying the learner around: keep the learner in one place and let every surface talk to it. Replication, CRDTs and event-log merging buy offline writes on several machines at once, which a single learner on a home tailnet rarely needs, at a price the schema measured below makes very high (§5.2).

- Tests find fixtures relative to the repository and ask git which fixture files are tracked (`tests/test_tracked_fixture_databases.py:35-41`).

- The chat frontend's user unit runs from the main checkout's `.venv` (`docs/reviews/mcp-c1a.md:107` on `mcp/c1-read-context`).

**A file at `canonical_uri` or `original_uri`.**
- **Registration** stores the import path as artifact identity: `canonical_uri = resolved.source`, `original_uri = file://…` (`src/learnloop/content/pipeline/add_source.py:242-249`), and an artifact is found again only by that string (`src/learnloop/content/sources/source_library.py:73-76`; `src/learnloop/content/pipeline/source_ingestion.py:1699-1711`). A book moved to another folder or machine becomes a second artifact.
- **The card's re-read** ("Read it again with text recognition") re-imports from `canonical_uri` (`src/learnloop_sidecar/handlers/first_run.py:336-345`). This is E1 (§3.1).
- **Extraction repair** re-acquires from `original_uri`, else `canonical_uri` (`src/learnloop/content/pipeline/jobs.py:2460-2465`).
- **Already store-first, correctly:** resuming an extraction reads the store and checks the hash (`src/learnloop/content/pipeline/source_ingestion.py:215-221`); the Reader, the PDF manifest and retrieval resolve the store first and fall back to a local file (`src/learnloop/ingest/originals.py:71-77`; `src/learnloop/reader/span_view.py:181-194`; `src/learnloop_sidecar/handlers/reader.py:549-553`; `src/learnloop/source_retrieval/b4.py:154`); `backfill_original` refuses bytes whose hash differs (`src/learnloop/ingest/originals.py:90-110`).
- **The desktop's protocols** read the originals and animation stores straight from the local vault path (`apps/learnloop-tauri/src-tauri/src/main.rs:19-52`), so a remote client needs an HTTP equivalent (§6.6).
- **Project capture hooks** write to an absolute local path (`src/learnloop/projects/hooks.py:56-75`), so repositories on a machine other than the vault's are not captured.

## 3. Problems, with evidence

### 3.1 git-LFS friction, and E1

- **Pointer files.** git-LFS leaves a ~130-byte text pointer in place of the file whenever the smudge filter does not run (git-lfs not installed, `GIT_LFS_SKIP_SMUDGE`, a quota-blocked download) [LFS-smudge] [GH-LFS-billing]. In the main checkout today all 22 `new_textbooks/*.pdf` are 130–134-byte pointers, while the local LFS store holds the 443 MB of real bytes.
- **E1 (found by the GLM-OCR live check, 2026-10-14; fix in flight on `fix/reread-safety`).** Every PDF source's `canonical_uri` points into `new_textbooks/` (§2.2). The card's re-read imports from that path (`src/learnloop_sidecar/handlers/first_run.py:336-345`), so it registered a new revision *from the pointer*, moved `current_revision_id` to it, failed extraction, and left the book unopenable from the Library, while doctor flagged nothing. `fix/reread-safety` makes the re-read read the store and refuse mismatched bytes. Two causes remain for this spec: repair still re-acquires from the path (`src/learnloop/content/pipeline/jobs.py:2460-2465`), and identity still is the path (§2.5).
- **Contributors pay for LFS.** Cloning needs git-lfs; every download by any clone or fork counts against the *owner's* LFS bandwidth (10 GiB on the Free and Pro plans); and once a quota is exhausted without a payment method, clones get pointer files only [GH-LFS-billing].
- **LFS objects cannot be removed by a commit.** Deleting a file leaves its LFS object on GitHub's storage; GitHub's only removal path is to delete and recreate the repository, or ask Support [GH-LFS-remove].

### 3.2 Binary SQLite in git

- **No merge.** Git cannot merge two versions of a database; one side wins. `linear_algebra/state.sqlite` alone was committed 31 times on `main`'s history, and the history now holds 81 distinct database blobs across 19 paths, 1,051 MB uncompressed.
- **A database in git is not a backup of a live database.** A committed `state.sqlite` misses whatever is still in its `-wal`; the repository guards against that with a session check and a fixture test (`tests/conftest.py:100-151`; `tests/test_tracked_fixture_databases.py:23-31`), which is effort spent keeping git from corrupting what git should not hold.
- **Every pull is the owner's whole history.** A contributor who clones gets the learner's database at every committed moment, and any test that touches a working vault can change it in place, which is why the session guard exists.
- **Tests move under the owner.** `tests/test_goal_decay_projection.py:21-24` records that pointing a golden at `fixtures/linear_algebra` "made the suite fail the moment anyone practised or created a goal in the working vault".

### 3.4 Multi-device use today

- **The tailnet path exists but stops at one machine.** The mobile host and the chat server attach to a vault on the desktop's disk (`src/learnloop_mobile/config.py:11-26`; `docs/specs/spec_mcp_frontend_c1.md` §3.3 on `mcp/c1-read-context`).
- **Only the desktop app does the primary work.** `SidecarContext.load` binds the ingest runner, syncs vault state, binds the post-attempt worker, refreshes the canonical projection, schedules cold probes, runs startup maintenance and resumes post-attempt jobs (`src/learnloop_sidecar/context.py:58-118`). The post-attempt worker is the sidecar's own (diagnose, embed and learner-text-gap slots over a durable, lease-fenced queue; `src/learnloop_sidecar/post_attempt_worker.py:1-14`). The mobile spec's secondary attach runs none of this (`docs/specs/spec_mobile_tailnet_v1.md` §3.1). As specified, then, a phone answer graded while the desktop app is closed waits for the desktop to open before its asynchronous diagnosis (ADR-016) runs.
- **Even a running primary finds other processes' work only when woken in-process.** The post-attempt worker starts on its first `notify()`, and `resume_post_attempt_jobs` notifies only when the queue holds work at load (`src/learnloop_sidecar/post_attempt_worker.py:12-14`; `src/learnloop_sidecar/context.py:180-192`). The ingest drain thread exits after three idle rounds and restarts only on an enqueue in its own process (`src/learnloop/content/pipeline/jobs.py:4751-4760`). Reproduced on 2026-10-14: with an empty queue at load, a job added afterwards left the worker not running. And a context whose ingest manager is not bound, as in the mobile spec's secondary attach, raises "Ingest jobs are not bound to a vault yet" on Add, re-read, repair or a Reader build (`src/learnloop/content/pipeline/jobs.py:3577-3580`).
- **Ports collide.** The mobile host's doctor requires a background Serve route on port 443 and Funnel off on port 443 (`src/learnloop_mobile/doctor.py:86-117`). The chat frontend's runbook points Funnel's port 443 at the MCP server (`docs/reviews/mcp-c1a.md:88-100`, open question Q3, on `mcp/c1-read-context`). Funnel visibility is per port [TS-Funnel], so both cannot hold on one machine.
- **A laptop has no way in** except the phone's PWA once M2a exists. The desktop app opens a local vault through a local sidecar only.
- **Copying the vault to the laptop is unsafe.** WAL needs every process on one host [SQLite-WAL], and the architecture rule already forbids syncing a live vault folder (`docs/learnloop-architecture-vault/Architecture/State and Persistence.md:85-90`).

## 5. Options

### 5.1 (a) A single-writer hub

**Shape.** One machine holds the vault on local disk. Every process that touches the database runs on that machine: the desktop app when the owner sits at it, the mobile host, the chat server and a headless primary. Other devices are clients over the tailnet: HTTPS to the hub, never file access.

**Why it fits.** It is the arrangement the mobile host (M1, built) and the chat server (C1a, built on its branch) already use; the multi-process story is SQLite's own (WAL, `busy_timeout`, one host) plus the locks that exist (`src/learnloop/db/connection.py:12`, `:105`; `src/learnloop/vault_lock.py:9-13`). Replay, table roles and migrations are untouched, because nothing merges.

**Variants for offline:**
- **a0, online-only.** Clients need the hub. Capture queues in outboxes (the phone already has them).
- **a1, read-only snapshot on the laptop.** When the laptop is reachable it receives a completed §6.7 snapshot (its databases copied by the backup API, with the YAML and originals that pair with them). The transfer may be restic, rsync, or `sqlite3_rsync` from the snapshot's closed database file, never from the live vault. Offline, the laptop can read the library and its history but not practise. Needs a read-only desktop mode: the sidecar today requires a writable vault (ADR-015 check 2).
- **a2, offline practice with deferred grading.** The laptop or phone records answers offline with the presented item's contract; the hub grades them on reconnect. This changes evidence semantics (served-offline coldness, reservations, backdated scheduling) and needs a playbook successor.

**Costs.** A headless primary and the primary-role lock (§6.2); PR-1..PR-7, which mobile M2 and chat C2 need anyway; a remote mode for the desktop app if the full UI is wanted on the laptop (§6.6). **Risks.** The hub is a single point of failure (backups, §6.7); the hub must be awake (D4); public ingress to the hub for chat (C1 risk R1).

### 5.2 (b) Event-log replication over LearnLoop's own ledgers

**Shape.** Each device keeps a full vault, appends its own rows, and ships them to the others; derived tables are rebuilt after each merge.

**What it would take, measured against the schema (§2.3):**
- **Device-scoped, globally ordered ids.** ULIDs are unique enough, but history is ordered by `(created_at, id)` from each machine's wall clock (`src/learnloop/ids.py:22-25`); merged histories need hybrid logical clocks, and replay order would change, so every merge is a potential persisted-meaning change (R5).
- **A merge rule for every non-derived table.** Only 19 of 321 tables are rebuildable. The other 302 include 82 mutable WORKFLOW tables (sessions, leases, plans, reservations) whose rows two devices would both edit, and RAW_LEDGER tables that hold mutable authoritative state (`activity_card_state`, `src/learnloop/db/table_roles.py:45-48`).
- **Decisions made against stale state.** Serving, reservation and exposure are decisions about the learner's current state: two offline devices can both serve the same cold check or held-out exam item, both spend a session's probe cap, or both reveal a solution before an independent check. A merge can only detect these after the fact; the evidence is then not what the coldness and certification rules assume.
- **Authored content.** Concurrent YAML edits would become proposals with a base content hash, applied through the existing write-ahead protocol (`src/learnloop/content/proposals/apply_protocol.py:1-21`), with conflicts sent to review.
- **Mechanism.** SQLite's session extension records changesets, but needs declared primary keys and skips virtual tables [SessionExt]; Python's standard `sqlite3` module does not expose it [Py-sqlite3], so it would mean adopting APSW [APSW-session] as a second driver.

**Verdict.** Months of work and a permanent tax on every new table, to support simultaneous offline writing by one person. Deferred with a trigger (§11).

### 5.4 (d) File sync (Syncthing, Dropbox, iCloud Drive, Nextcloud)

**For live databases: never.** A WAL database is `state.sqlite` plus `-wal` and `-shm`; a sync client can upload them from different moments or replace one without the other, and WAL "does not work over a network filesystem" because its index is shared memory on one host [SQLite-WAL] [SQLite-corrupt §1.2, §1.4, §2.5]. The repository's architecture rule says the same (`docs/learnloop-architecture-vault/Architecture/State and Persistence.md:89-90`). Two hosts each running LearnLoop on a synced folder would also each take their own `fcntl` lock, so the vault mutation lock would protect nothing (`src/learnloop/vault_lock.py:9-13`).

**For closed artefacts: fine.** Content-addressed originals, finished backups and a laptop snapshot made with the backup API can be copied by any tool, because nothing writes them in place. Syncthing (MPL-2.0, v2.1.6) would work for that, but the hub can serve the same files itself (§5.5).

### 5.5 (e) Blobs: the content-addressed originals store

The store already is what (e) asks for: `canonical-sources/raw/sha256-<hex>`, written atomically with fsync, idempotent, and verifiable against each revision's `asset_hash` (`src/learnloop/ingest/originals.py:23-53`). It lives inside the vault, so it leaves git when the vault does.

**What changes:**
- **The hub serves it.** An authenticated `GET /api/v1/originals/sha256-<hex>` on the private host, with the same content-addressed-name rule as the desktop's `llpdf://` handler (`apps/learnloop-tauri/src-tauri/src/main.rs:19-52`) and the Reader's permission check (`_require_source_reader` in `src/learnloop_sidecar/handlers/reader.py:546-547`).
- **The store becomes the only authority for bytes** (§6.4).
- **Off the hub:** it is part of every snapshot and of the hourly restic copy, which transfers only what changed [restic].
- **Not needed now:** a store shared across vaults, or object storage as the primary store. The three vaults' originals total 229 MB (§2.2).

### 5.6 (f) Authored content: text export or the database as authority

Authored knowledge is already text (YAML and Markdown) and stays the authority for what it holds; evidence stays in SQLite. Some authored definitions live only in the database (activity cards, families and patterns are RAW_LEDGER rows), so a YAML-only git history would never be a complete copy of the learner.

**Options:**
- **f0.** Versions come from backups only.
- **f1.** The hub keeps an optional *private* git repository of each vault's text files (excluding `state.sqlite*`, `.learnloop/`, `canonical-sources/`, `projects/*.sqlite`, `.env`), committed automatically after each accepted change, never pushed to the code repository, and never used to move data between machines.
- **f2.** A full JSONL export of the database as the authority. Rejected: it inverts the authority model and duplicates replay.

**Recommendation:** f0, with f1 as an opt-in (D11). The owner's request was about sharing *code*; the vault's history is the owner's, and the backups version it.

### 6.2 Roles: the hub, the primary role, and clients

**The hub** is the one machine that holds a vault. It is a role, not a product: any LearnLoop install is its own hub, which is why a contributor's laptop or a new learner's first launch works unchanged (R10).

**The primary role.** Exactly one process per vault runs the primary duties of `SidecarContext.load` (`src/learnloop_sidecar/context.py:58-118`): binding the ingest runner, content sync, adopting reference questions, the post-attempt worker, the projection refresh, cold-probe scheduling, startup maintenance, resuming post-attempt jobs, key-check recovery and reading-build reconciliation, plus, new here, queue discovery (below).
- **The lock.** The role is an exclusive `fcntl.flock` on `<vault>/.learnloop/primary.lock`, held while a process has that vault loaded as primary. It is released on exit, death or a switch to another vault, like the vault lock (`src/learnloop/vault_lock.py:9-13`). An OS lock suffices because the hub model guarantees one host; a database lease would add a migration and a heartbeat for nothing.
- **Who takes it.** `learnloop hub serve` takes it at start and waits if it is held. The desktop sidecar tries it without waiting each time it loads a vault: if it gets it, it runs `load()` as today; if not, it attaches as a secondary (next item) and retries every 30 s, promoting itself with a full `load()` once the role is free (the hub service stopped), no update mark exists (neither the deployment's nor the vault's) and the vault's schema matches its code (below).
- **The desktop as a secondary keeps every feature (PR-8).** The mobile spec's `load_secondary` leaves the ingest manager unbound, so on its own it would make Add, re-read, extraction repair, Reader builds and job control raise "Ingest jobs are not bound to a vault yet" (`src/learnloop/content/pipeline/jobs.py:3577-3580`), and the hub's ingest manager lives in another process. The desktop secondary therefore binds the ingest manager in a *submit-only* mode:
  - it enqueues batches and jobs, reads their status, and records cancel and resume requests, all as durable rows (the queue, the `cancel_requested` flag and the reading requests in `source_auto_build_state` already are durable);
  - it never drains, runs the reading sweep, recovers leases or acts on a reading request, and never runs a job in the caller (today a manager bound with `background=False` drains in the caller, `jobs.py:4693-4696`);
  - stopping a running provider call becomes a durable cancel: a running job already stops at its next checkpoint when its batch is flagged (`src/learnloop/content/pipeline/runner.py:383-390`), and the primary also interrupts its own live call when its queue discovery sees the flag, because the interrupt handle is held in the executing process (`runner.py:564-575`);
  - after an applying job completes, the desktop reloads from the job's durable status and its vault watcher, not from the in-process set of reloaded jobs.

  This holds on first attach, on every `reload()`, and on a vault switch, which releases a primary lock the desktop held and tries the new vault's. A desktop that promoted itself keeps the role until it quits or switches vaults; the hub service, waiting on the lock, then takes it. Either holder runs the same duties, so nothing waits in between. An upgrade does not rely on that hand-back: it asks the owner to quit the app first (below).
- **Work runs with the primary's environment.** A job the desktop submits, and the diagnosis of an attempt made on any surface, run in the primary's process, so its routes and extraction capabilities apply, not the submitter's. A route override set in a shell (`LEARNLOOP_AI_PROVIDER`, read per process: `src/learnloop/ai/routing.py:247-249`, `:308-310`) or an optional extra installed in one environment (`pdf` for Marker, `glm-ocr`) must therefore be set in the unit and in the deployment checkout's environment. `learnloop hub doctor` and the desktop's Settings show the primary's effective routes and installed extras, and the desktop says when they differ from its own.
- **Queue discovery from startup.** A primary that started with empty queues must still find what other processes queue (§3.4). The primary therefore:
  - starts its post-attempt worker and ingest drain at `load()`, whatever the queues hold;
  - watches for other processes' commits with `PRAGMA data_version` on a dedicated connection once a second [SQLite-data_version], and on a change checks the post-attempt, learner-text-gap, ingest, reader-request and question-promotion queues and the cancel flags of the jobs it runs;
  - rescans every queue every 30 s regardless (the existing idle poll, `src/learnloop_sidecar/post_attempt_worker.py:32`, and the reading sweep, `jobs.py:3489`).

  **Dispatch bound:** an idle primary claims a job committed by any process within 5 s (normally about 1 s). The model call that follows takes as long as it takes. `learnloop hub doctor` shows the age of the oldest unclaimed job. The same discovery runs when the desktop app is the primary (no hub service), which the mobile spec's M2 needs as well (§6.9).
- **One code version per vault, one upgrade per deployment.** The services run from the deployment checkout (D13), but the desktop app launches its sidecar from the source checkout it was built in (`apps/learnloop-tauri/src-tauri/src/sidecar.rs:372`, `:640-645`). A development build must never migrate the owner's vault to an unreleased migration: migration numbers are renumbered when branches land. So:
  - a vault under the data root is migrated only by a process running from the deployment checkout, and only after a pre-migration snapshot (§6.7). Its `learnloop.toml` records which process (a `[hub]` setting). From S1, `migrate = "deployment"`: no hub service exists yet, so the desktop app built from the deployment checkout migrates it at load as today, after a snapshot (S1 adds that step), and a build from any other checkout does not. From S5, when the owner enables the hub service, `migrate = "service"`: only `learnloop hub serve` migrates it. `vault move`, run from the deployment checkout, migrates its copy once, after the copy's first snapshot (§7.1 step 4), and then writes the setting;
  - every process the setting does not name, the desktop app included under `service`, attaches to such a vault only when its schema matches the code, and otherwise refuses with a plain message ("This app and your LearnLoop service are different versions: update the service, or open the app built from it"; under `deployment`, "… open the app built from your LearnLoop install"); promoted to primary, it still never migrates it;
  - before S5 an upgrade is: quit the app and stop every unit that runs from the deployment checkout (the mobile host and the chat server, once they have moved there), move the checkout to the tag, starting nothing until it is done, reopen the app, which snapshots and migrates the vault it opens, and open each other vault of the deployment once the same way before starting the units again; a unit started earlier refuses a vault the app has not yet migrated, with the plain message above. With no service waiting on the primary role, nothing before S5 can deadlock; a failure part-way is handled as below;
  - **from S5, one upgrade barrier covers the whole deployment.** The resource an upgrade changes is the deployment checkout, and every process that runs from it shares it whatever vault it opens: each vault's hub unit (one instance per vault), the mobile host and the chat server (whose units run from one checkout's environment, `deploy/learnloop-mobile.service:7-9`), the desktop app built there and the CLI. A barrier per vault is not enough: while vault A is being quiesced, a desktop opened on vault B would attach, could promote itself, and would then run across the checkout change. Restarting the units is not enough either: a desktop that promoted itself while the service was stopped holds the primary role until it quits, so the restarted service would wait on it while the desktop, forbidden to migrate, kept it. And a lock released before the checkout changes would let a process start in between, load the old code and run on after the change. So there are two locks and two marks, and the upgrade holds the deployment's lock exclusively from quiescence until the new code is in place:
    - **the deployment's lock and mark.** The lock is `.learnloop/deploy.lock` in the deployment checkout (`.learnloop/` is ignored at any depth, `.gitignore:197`). Every entry point that runs from the checkout (each unit's `ExecStart`, the desktop app's launcher and the owner's `learnloop` command) starts through a launcher step that takes this lock shared **before any application code from the checkout is loaded**: util-linux's `flock --shared --no-fork <lock> <program>`, which waits until the lock is available and then becomes the program, which keeps holding it until it exits [flock-1]. While the upgrade holds the lock exclusively, a launch therefore blocks before it has loaded anything, and starts on the new code once the lock is released. A process started without the launcher takes the same lock without waiting before it attaches (the checkout root is the one `default_migrations_dir()` already resolves, `src/learnloop/db/migrate.py:40-41`) and exits with "LearnLoop is updating" if it cannot; the steps the upgrade and its abort run themselves inherit the upgrade's lock. The mark is `.learnloop/update` beside the lock. Every process checks it once it holds the lock and again before every attach (first attach, `reload()`, a vault switch); while it exists, no process from the checkout attaches to any vault except the hub services the upgrade starts from the marked tag and read-only inspection (`learnloop hub doctor`; ADR-008's read-only open), and a desktop app shows "LearnLoop is updating" and retries;
    - **each vault's.** Every LearnLoop process that opens a vault, from any checkout, primary or secondary and the CLI included, holds a shared `flock` on `<vault>/.learnloop/attach.lock` while it does, and checks for `<vault>/.learnloop/update` before attaching; while that mark exists, only the vault's hub service from the marked tag attaches. These cover a development build, which takes its own checkout's deployment lock, not this one's.

    The owner upgrades with `learnloop hub upgrade <tag>`, which:
    1. stops every hub, mobile and chat unit of the deployment, for every vault;
    2. takes the deployment's lock exclusively, waiting until no other process from the checkout runs. If the desktop app or a CLI command still holds it, the command names it ("Quit the LearnLoop app to continue the update") and waits; it never kills a process. From here to step 5 every launch blocks in its launcher;
    3. holding that lock, writes the deployment's update mark (the target tag, its schema, and the deployment's vaults: every vault one of its hub units pins, which `learnloop hub doctor` already reads, §6.3) and each of those vaults' marks, then waits until no process from another checkout (a development build) has one of the vaults open, taking each vault's attach lock exclusively and releasing it;
    4. still holding it, moves the deployment checkout to the tag and syncs its environment (rebuilding the desktop app if the tag changed it). Nothing runs from the checkout while it changes, and nothing can start;
    5. releases the deployment's lock once the new code and environment are complete: launches that were blocked start on the new code and wait on the marks. It then starts every vault's hub service. Each takes its vault's primary role, then a complete, verified pre-upgrade snapshot (§6.7), migrates, and then holds the role and runs no primary duty until the marks are gone, so nothing can promote and nothing writes to a migrated vault while another is still migrating. A snapshot that is incomplete or fails verification stops that vault before any migration;
    6. once every vault's applied migrations are the tag's, removes every vault's mark and then the deployment's (the services start their duties), and starts the secondary units. The owner reopens the desktop app, whose sidecar runs from the checkout it was built in (`repo_root()` is fixed at build time, `apps/learnloop-tauri/src-tauri/src/sidecar.rs:640-645`), now at the new code, and attaches as a secondary.

    A vault left at `migrate = "deployment"` (no hub unit) is outside the list and migrates when the desktop app next opens it, after its snapshot, as before S5.
  - **A failed upgrade leaves a vault between versions.** ADR-008 makes each migration atomic with its ledger row, not the sequence: `apply_migrations` commits each migration before starting the next (`src/learnloop/db/migrate.py:84-88`; one `BEGIN IMMEDIATE` … `commit()` per migration, `:189`, `:209`). If 203 commits and 204 fails, the database keeps 203 (reproduced on 2026-10-14 on a scratch database), a schema that the previous tag's code refuses under this rule. So a failure stops that vault's service, and the barrier stays: every mark remains and every vault of the deployment stays closed. `learnloop hub doctor` names the vault, the migration that failed and the last that committed, and reports a mark older than an hour. The owner then chooses:
    - **repair forward:** `learnloop hub upgrade <fixed-tag>` to a tag whose migrations complete from where it stopped (migrations apply from the first unapplied version, as they always do);
    - **abort:** `learnloop hub upgrade --abort` runs, in this order and with every mark still in place:
      1. stops the deployment's units and takes the deployment's lock exclusively, as in steps 1–2 of an upgrade;
      2. returns the checkout to its previous tag and syncs that environment (rebuilding the desktop app if needed), still holding the lock. This comes first because only the previous code expects the snapshots' schema: the failed tag's doctor would report the restored vault's newer migrations as missing (`sqlite:migrations_missing`, `src/learnloop/ops/doctor.py:966-974`), and its replay may need tables the snapshot lacks;
      3. with that previous code, restores the verified pre-upgrade snapshot of every vault of the upgrade whose applied migrations differ from it (the failed one, and any that already migrated, since the previous code refuses them too) into a new directory by §6.7's restore, which validates it: manifest, apply-intent recovery, doctor, shadow rebuild, originals sweep. A restore that fails validation stops the abort here, with the barrier still up;
      4. switches every pin to the restored directories (§6.3);
      5. removes the marks, releases the lock and starts the units.

      The partly migrated directories are kept for the owner to retire; nothing restores over them. No work is lost: nothing has attached to those vaults since their snapshots.

    Before S5 the same two choices apply by hand, in the same order: a fixed tag; or, with the app quit and nothing started meanwhile, the checkout returned to its previous tag first, then `learnloop restore` (run with that code) of the pre-migration snapshot the desktop app took, then the pins switched to it.
- **Synchronous work started by a secondary.** A synchronous synthesis run started from the desktop app while the hub service is primary records its owner (process id and boot id). The primary's abandoned-run sweep finalizes only runs whose owner is gone. The mobile spec's PR-3 put durable ownership of synchronous runs out of scope; with a separate primary it is in scope (PR-8).
- **The hub service also re-syncs vault content** when the content fingerprint changes (the mobile spec's `vault_content_fingerprint`, §3.1), once PR-2 makes content sync safe beside attempts. It serves nothing over the network; the network surfaces stay in the mobile host and the chat server.
- **Supervision.** A `systemd --user` unit (one instance per vault), restarted on failure. Holding the primary role, it migrates an older schema under the vault lock after a pre-migration snapshot (ADR-008, §6.7); it exits 78 on a database newer than its code, so the supervisor does not loop.
- **Why a third process.** The mobile host could hold the role, but then the tailnet-facing process would also migrate the vault and run every AI route. Kept apart, either can restart alone, and the owner can run the hub service with chat only. The cost is one more user unit.

**Secondary hosts** stay as built or specified: the mobile host (`learnloop-mobile serve`, mobile §3.1) and the chat server (`learnloop mcp serve`, C1 §3.3) attach without migrating, run no primary duties, and write through domain services. Because the primary runs continuously and discovers their queued work (above), a phone attempt's diagnosis is claimed by the hub's post-attempt worker within the dispatch bound and finishes when its model call does, not when the desktop app next opens (R2).

**Clients** never open the database: the phone's PWA and Shortcut, a laptop browser, the laptop's remote desktop mode (S6), and the chat hosts.

**Ingest and AI calls run on the hub.** Provider keys stay in the hub's machine-global config (R9). A laptop that adds a local PDF uploads it to the hub (S6; until then, through capture), which stores it, registers it and imports it.

### 6.3 The data root

**Layout on the hub (D5):**
- `~/learnloop-vaults/<name>/` for each of the owner's existing vaults. The product default stays `~/LearnLoop`, created on first launch (`apps/learnloop-tauri/src-tauri/src/sidecar.rs:735-745`); a new learner never sees the vaults folder.
- `~/learnloop-books/` (or any folder the owner chooses) for personal PDFs not yet imported. LearnLoop never reads from it after import.
- `~/learnloop-backups/` for local snapshots (§6.7). It is on the hub's disk, so it is for quick restores after a mistake, not protection against a dead disk.

**Rules:**
- **No vault inside a git working tree.** Doctor gains `storage:inside_git_worktree` (a warning). Existing checks stay: `storage:network_filesystem` (`src/learnloop/ops/doctor.py:889`) and the sync-folder rule.
- **A vault's database lives inside its directory.** Under the data root `storage.sqlite_path` is the relative `state.sqlite`; doctor gains `storage:database_outside_vault` (an error there, a warning elsewhere) for an absolute path, a path through `..`, or a symlink out of the vault. `vault move` and `restore` write it that way (§7.1).
- **Every surface pins the vault by absolute path:** the desktop's `last_vault`, `mobile.toml`'s `vault` (mobile D15), the chat unit's `--vault`, and the hub unit's `--vault`. `learnloop hub doctor` reports any pin that differs.
- **Services run from a deployment checkout** (D13), for example `~/learnloop-app` at a tag, not the development checkout, where agents' worktrees and tests run. The desktop app the owner uses on these vaults is built from it too; a development build attaches only at a matching schema and never migrates them (§6.2).

### 6.4 Sources and originals: no path dependency (E1, completed)

1. **The store is the only authority for bytes.** Every path that needs an existing revision's bytes reads `stored_original_path(vault, asset_hash)` and checks the hash. This means re-read (done on `fix/reread-safety`), extraction repair (`src/learnloop/content/pipeline/jobs.py:2460-2465`, to change) and any re-import of an existing source. If the store copy is missing, the learner sees "the file this book came from is missing; add it again", never a silent re-registration.
2. **`canonical_uri` for a local file is provenance.** It is kept, shown as "added from …", and never opened for an existing revision.
3. **Local files have content identity.** When a local file is imported, `register_source_revision` first looks for an existing revision with the same `asset_hash` under an artifact of the same `acquisition_kind` whose `canonical_uri` is a local path. If one exists, it reuses that artifact and appends the new path to `source_artifact_locations` (new, RAW_LEDGER, append-only: artifact id, location, recorded at). `source_artifacts` rows are never rewritten (ADR-007). A moved or re-copied book is then the same book, on any machine.
   - No algorithm successor: source identity is not scoring, scheduling or a projection.
   - It does change import dedup, so it ships behind `ingest.content_identity_for_local_files` (default on) with a doctor line counting merges.
4. **Doctor:**
   - `sources:original_missing` (error): a current revision without a store copy;
   - `sources:path_is_lfs_pointer` (warning): a local `canonical_uri` that is a git-LFS pointer;
   - `sources:revision_without_reading` (error; from `fix/reread-safety`).
5. **Capture media and uploads** already go to the store (mobile spec §6.7); S6's laptop upload uses the same call.

### 6.6 Offline behaviour, by surface

The tailnet is not a home LAN: devices connect directly or through Tailscale's relays when a direct path fails [TS-DERP], so "away from home" is "reachable" whenever both ends have internet.

| Surface | Hub reachable | Hub unreachable (asleep, off, or no internet on either end) |
|---|---|---|
| Desktop app at the hub | Everything, as today | It is the hub |
| Phone | Mobile M1–M3 | Capture outbox (mobile §7); "Your LearnLoop at home is offline"; no practice (mobile D9) |
| Laptop browser (the PWA) | Capture; dailies from M2a; the tutor from M3 | The same outbox and message as the phone |
| Laptop remote desktop mode (S6) | The full desktop UI | "Your LearnLoop at home is offline", unless S7's read-only snapshot is enabled, then reading and history only |
| Chat (ChatGPT, Claude) | C1 tools now, C1b and C2 later | The host reports a connection error; LearnLoop records nothing; the conversation continues without LearnLoop |
| The hub without internet | Everything local; AI routes fail as they do today | — |

**The remote desktop mode (S6, sized here, specified when its trigger fires).**
- **Transport.** The desktop's single `call()` (`apps/learnloop-tauri/src/api/client.ts:308-315`) switches from Tauri `invoke` to the hub's `/rpc` adapter (mobile §6.2) with a `desktop` token scope and the `desktop` device class.
- **Protocols.** `llpdf://` and `llmedia://` fetch from the hub's originals and media endpoints instead of the local disk (`apps/learnloop-tauri/src-tauri/src/main.rs:19-52`).
- **No local vault machinery:** the vault watcher and the local sidecar launch are off.
- **File pickers become uploads.**
- **Allowlist.** The `desktop` scope allows the 355 registered sidecar methods minus a short deny list: `run_cli_command`, `sqlite_admin`, vault create, select and load (the hub pins vaults), and local file operations.
- **Size:** medium to large, mostly Rust command plumbing.

**Day boundaries.** "Today" is the hub's local date (`src/learnloop/daily_plan/engine.py:150-153`). A learner travelling across time zones sees the hub's day (D15).

| | Default | Notes |
|---|---|---|

### 6.12 Opt-in data contribution toward an n>1 model (R13; deferred phase S9)

**Why now.** The owner wants learners to be able, one day, to contribute their traces to a shared, n>1 learned model. Nothing is collected or built here. This section fixes what LearnLoop's data model must guarantee now, so that contribution needs no retrofit once more learners have vaults: identity, versions, the boundary between structure and text, and consent.

**What exists.** `learnloop dataset-export` writes a reproducible local dataset from a backup-API snapshot, with a versioned manifest (`DATASET_VERSION`, `COLLECTION_VERSION`, `LABEL_VERSION`, schema hash, migration list, split policy; `src/learnloop/substrate/dataset.py:46`, `:692-748`; `src/learnloop/outcome_contract.py:13-14`). It is a *full-fidelity research export for the learner's own use*: it keeps `snapshot.sqlite` and every RAW_LEDGER and RECEIPT table verbatim (`dataset.py:670`, `:716`), so it carries extracted book text, answers, notes and model output. It is never a contribution format. The contribution export is a separate, allowlisted projection that reuses its snapshot and versioning machinery.

**Requirements for the contribution export (S9).**
1. **Versioned and documented.** Its own schema version and a published data dictionary. It is built from a §6.7 snapshot, never from a live database. Each record keeps what is needed to interpret it: the algorithm version; the grader, diagnoser and router versions and model ids from the model-call receipts; the item's content hash and kind; concept and misconception ids; and the source's public identity (DOI, arXiv id, ISBN or URL) only when one exists and the consent scope includes sources.
2. **Coverage.** Attempts and their grades; diagnoses and misconception attributions; measurement events and observations; scheduling and serving decisions (receipts); session and timing events; the concept graph's structure (ids and relations, not text).
3. **Pseudonymous learner ids.** A vault mints a random contributor id at its first consent; a learner with several vaults on one hub (the owner has three) may reuse one vault's id for the others at consent, so that one learner is one id, or keep them apart. It is never derived from a name, email, device token, endpoint token or path, is stored in the vault, and is used only in contributions. The existing `learner_id` columns, which default to `'local'` because a vault is one learner (for example `migrations/072_commitments.sql:54`, `migrations/079_progression_and_lapse.sql:40`), map to it at export. Pseudonymous is not anonymous: one learner's trace, timing and reading list can identify them, and the consent text says so.
4. **Consent: recorded, scoped, revocable.** Consent is an append-only record: its scope (which record kinds, which subjects, whether any free-text category is included, whether source identities are), the version of the consent text, and when. A revocation is a later record. No export runs without a current consent that covers its scope, and a revocation stops future exports.
5. **Redaction by default.** Excluded unless the learner opts a category in after previewing it: all source text (extracted blocks, document IR, quotes, retrieved passages, captured provider output that quotes sources) and all personal free text (answers, explanations, notes, chat and tutor turns, capture text, grader and diagnoser rationales). Answers and extractions can quote copyrighted books, so opted-in free text is still checked against the vault's own source blocks and quoted spans are removed. The export is an **allowlist** of columns: a new table or column stays out until it is classified, the same discipline as table roles (ADR-003).
6. **Time.** Timestamps are shifted to an origin fixed per contributor id at first consent, keeping order and spacing (which spaced-practice models need) and lining up a learner's successive contributions, and dropping calendar dates and time zones.
7. **Withdrawal.** At first consent the vault also mints a withdrawal secret, kept with the consent record (and so in the encrypted backups) and never exported. Presenting it to the dataset store removes that contributor's partition from every later release. Releases already downloaded, and models already trained on them, cannot be recalled; the consent text says so plainly.
8. **A data licence distinct from the code licence** (D18), named in every release.
9. **A separate home.** Contributions live in a dataset store separate from the code repository: a dataset repository or object store with versioned releases, never the code repository (R6). The code repository holds only the exporter, the data dictionary and a synthetic sample built by the test builders.

**How it relates to the hub and replay.** A contribution is a one-way export from a hub snapshot. It is not a sync peer: contributed data is never imported into any vault, never replayed and never merged as evidence, so ADR-007 and replay are untouched. A model trained on pooled data comes back into LearnLoop only as a versioned artefact (priors or parameters) through the algorithm-change playbook, like any other change of persisted meaning.

**Constraints in force from now on** (cheap now, expensive to retrofit):
- New evidence tables keep structured fields and free text in separate, named columns, so redaction is a choice of columns rather than parsing a JSON blob. A JSON column that can hold learner or source text says so in its migration.
- Evidence keeps its version stamps (algorithm version, model ids in receipts, item content hashes); a change that drops one goes through the playbook.
- No device token, endpoint token or path becomes a learner identifier.
- Exports read backup-API snapshots only (R4).

S9's triggers are in §11 and its gates are G14.

4. **Move:** `learnloop vault move <v> ~/learnloop-vaults/<name>`.
   - **It resolves the database before copying.** `VaultPaths` joins `storage.sqlite_path` to the vault root, and nothing constrains it, so an absolute path or one through `..` names a database outside the vault (`src/learnloop/vault/paths.py:19-21`; `src/learnloop/config/schema.py:9-10`). A tree copy then carries no database. With an absolute path, the copy's unchanged config still names the *source's* file, so migrating or using the "copy" changes the source; with a `..` path it names whatever sits at that place beside the destination: the source's file when both share a parent, otherwise a missing one. A database without the `.sqlite` suffix is byte-copied with its `-wal` and `-shm` unless it is named in `database_names` (`src/learnloop/db/copies.py:103-134`). A symlinked `state.sqlite` is followed and copied through the backup API into a real file. All four reproduced on 2026-10-14 with `copy_tree_with_databases` on synthetic files. So the move leaves the configured database out of the tree copy, copies it once through the backup API to `<dst>/state.sqlite`, and rewrites only the *destination's* `learnloop.toml` to the relative `state.sqlite`. A database outside the vault, a symlinked database, or one named by another vault's config is listed, and the move refuses until the owner confirms each one. Afterwards it re-reads the destination's config and checks that its database is inside `<dst>` and is not the source's file (different device or inode).
   - It copies every other database through the backup API too (nested ones such as `projects/project_store.sqlite`), verifies, takes the first snapshot (§6.7), migrates the copy under the vault lock, runs doctor and `rebuild --shadow` (replay identical), checks that the source did not change during the copy, and only then updates `last_vault`, `mobile.toml` and the unit files.
   - **Project hooks.** An enrolled repository's `post-commit` hook appends to the vault's `projects/pending.jsonl` by absolute path (`src/learnloop/projects/hooks.py:56-75`), so after a move it would keep writing to the old vault. For each enrolled repository with a hook, the move shows the hook and, on the owner's confirmation, reinstalls it for the new vault (`learnloop project install-hook`; it replaces only its own marked block and keeps the rest of the hook, `src/learnloop/projects/hooks.py:106-133`). Lines appended to the old pending list after the copy are appended to the new one; the sweep reads from its stored byte offset (`src/learnloop/projects/capture.py:1007-1013`), so each is read once. A test commit in one enrolled repository confirms capture at the new location. The hooks live in the owner's other repositories, so an agent never edits them. (Capturing projects that live on another machine is a separate deferral, §11.)
   - **The source stays untouched,** and the destination provably does not share its database.
5. **Use the new location.** From the move on, the new location is the vault. The old directory is a frozen pre-move copy, not a live fallback: going back to it would lose everything done since. The fallback is the §6.7 snapshots, the first taken by the move. The owner retires the old directory after a week by default, once a complete off-host snapshot exists and a restore drill has passed. A directory still tracked by git (the working vaults under `fixtures/`, until S0) is retired only by step 6 when the owner lands S0; until then it stays in the checkout as a frozen test fixture, never a vault in use.
6. **Untrack the old copies (S0), and what that does to other checkouts.** `git rm -r --cached` keeps the files only in the checkout where it runs. When another checkout, the owner's main checkout included, is updated to that commit, git deletes the clean tracked files there, and refuses to update while they have local changes (the working vaults' databases usually do). Both reproduced on 2026-10-14 in a scratch repository. So:
   - before such a commit lands, the owner has a verified copy of each affected vault outside every checkout (step 4's destination and its first complete snapshot, or, if S0 lands before S1, a `copy_tree_with_databases` copy kept as a backup);
   - the owner updates the main checkout by first moving each untracked directory out of it with nothing open, as a rename on the same filesystem, and then merging; git applies the deletion cleanly and the moved directory keeps every byte (also reproduced). After S1 the directory goes to `~/learnloop-retired/<name>-<date>`; if S0 lands first, a working vault goes to `~/learnloop-vaults/<name>` and stays the live vault there (its config's relative `state.sqlite` moves with it). The owner then re-points every pin at once: opens the moved vault in the desktop app once (which records `last_vault`) and updates `mobile.toml`, the chat unit's `--vault` and any enrolled project hook (step 4). Without that, a desktop whose remembered vault is gone silently opens the first vault under `fixtures-local/` or creates `~/LearnLoop` (`apps/learnloop-tauri/src-tauri/src/sidecar.rs:671-679`, `:748-755`, `:735-745`). Until S1 the desktop app stays that vault's primary and migrates it as today; S1's move for it then reduces to the first snapshot, the `[hub]` setting (§6.2), the backups and the doctor checks;
   - a commit that untracks or deletes `fixtures/linear_algebra`, `fixtures/probability`, `fixtures/arxiv_v2` or `new_textbooks/` is landed onto the main checkout by the owner, never by an agent's landing step;
   - deleting retired directories is the owner's step; an agent never deletes them.
7. **Textbooks.** The real bytes are in the local LFS store (443 MB) and in any checkout where LFS smudged them. The owner, or a stage the owner authorizes, materializes them from the local store (no network: `git lfs checkout` reads `.git/lfs/objects`), checks each against its pointer's `oid`, copies them to `~/learnloop-books/`, and only then lets S0 untrack them. Already-imported books need nothing: their vault stores hold the bytes.

### 7.4 The public history (owner decision; never done by an agent)

**Decided (D1): the repository stays public.** What remains is what its history already serves (§3.2, §3.3): 81 database blobs with the owner's attempts and extracted book text; textbooks in plain git (Axler, Blitzstein and Hwang, MIT course PDFs) and in LFS (23 objects, among them shadow-library copies and instructor's manuals, §3.5); third-party exam text. S0, and S3 for the historical fixtures, remove it from the tip only, and S0 waits for the owner's trigger (§6.11), so until then the tip serves it too. Old commits stay reachable by hash through raw and LFS media URLs, and the refs of the 6 pull requests keep old commits reachable on GitHub even after a force-push [GH-sensitive].

**What no option changes.** The public fork (since 2026-07-21) and every existing clone keep what they copied, and GitHub cannot contact the fork's owner for you [GH-sensitive]. Deleting a public repository does not delete its forks [GH-delete]. Every option below only stops *new* downloads from the owner's repository.

| Option | What happens | For a public project that wants contributors |
|---|---|---|
| **H1. A clean public repository under the same name (recommended)** | At a quiet point after S0 (best after S3, when the tip's layout is final), from a fresh mirror clone: the owner rewrites history with `git filter-repo --sensitive-data-removal`, stripping by blob id every version of the private and third-party files that the tip no longer carries (`--strip-blobs-with-ids` [filter-repo]; by id rather than by path, so the sanitized `migration_head_*` on the tip survives while every earlier version of it goes); renames the old repository (for example to `learnanything-old`); creates a new public `6up-b/learnanything` and pushes the rewritten history to it; then deletes the old repository, which takes its LFS objects and pull-request refs with it, or makes it private (its public fork is then detached into its own network [GH-visibility]). Creating a repository under the old name ends the rename redirect [GH-rename], so existing links reach the clean repository | Keeps the URL contributors will use and the history (rewritten), needs no GitHub Support ticket, and costs little now: 1 star, 6 pull-request pages and the fork link (the fork stays public with the old data under every option). Every commit hash changes: the owner keeps the old mirror privately with filter-repo's commit map, so old hashes in review records can still be looked up, and every agent branch and worktree is recreated from the new history |
| **H2. Rewrite in place** | The same rewrite, force-pushed to the existing repository (`git push --force --mirror`), then a GitHub Support request to dereference pull-request refs, remove cached views and purge the orphaned LFS objects [GH-sensitive]. Deleting and recreating the repository is the only self-service way to drop LFS objects [GH-LFS-remove] | Keeps the star and the pull-request pages, though their diffs may break. The purge depends on Support, which acts only once no fork still references the data and only for data it judges sensitive [GH-sensitive]. The public fork does reference it, and third-party books may not count as sensitive, so LFS objects and pull-request refs may stay served. The same hash churn as H1 |
| **H3. Clean the tip only** | S0, and nothing more | Cheapest. Nothing is purged: the owner's learning history and the book copies stay downloadable from old commits, and LFS downloads keep counting against the owner's bandwidth [GH-LFS-billing] |

**Recommendation: H1.** It removes the data from the owner's repository without depending on Support, keeps the URL, and its continuity cost is lowest now; its hash churn grows with every branch, review record and contributor, so it is best done once, soon after S3 and before contributors are invited. H3 is an honest choice if the owner judges the exposure acceptable; this spec then records it as decided.

Agents never change visibility, rewrite history, force-push, or create, rename or delete a repository. H1 and H2 run as owner-run procedures from a fresh mirror clone, which the owner keeps as an offline archive.

## 9. Risks

- **The hub is a single point of failure.** Mitigated by §6.7: a copy on another device every hour, and the age of the newest one shown, not hidden.
- **The hub sleeps.** Dailies away from home fail exactly when the owner wants them (D4).
- **Public ingress lands on the machine that holds the learner.** The MCP surface stays narrow (C1 risk R1) and on its own port (§6.5); OAuth stays the chat frontend's follow-up.
- **Re-pinned goldens hide a regression.** Each re-pin is listed with its old and new values in the stage record, and the `owner_vaults` lane keeps the real-data checks.
- **The move happens while something writes.** `vault move` takes the primary lock itself, the owner stops the other services first (§7.1 step 2), and the copy goes through the backup API in any case. Because a write to the old location after the copy would be lost, the move refuses to switch the pins if a second backup-API snapshot of the source differs from the first (G1).
- **A database configured outside the vault.** A copy of such a vault would share the source's database; the move and restore resolve it and refuse until confirmed (§7.1 step 4, G1).
- **Untracking deletes files in other checkouts.** Updating any checkout to an untracking commit deletes its clean copies of those files; the owner copies the vaults out first and lands such commits (§7.1 step 6).
- **Version skew.** A development build could migrate the owner's vault to an unreleased migration; under the data root only code from the deployment checkout migrates (the desktop app built there until S5, the hub service from S5), apart from `vault move`'s one migration of its copy (§6.2).
- **An upgrade waits for the desktop app, on every vault.** The deployment checkout is shared by every vault's processes, so `learnloop hub upgrade` needs every process of the deployment closed, whatever vault it has open; it asks the owner to quit the app and waits, and never kills a process. Nothing attaches to any of the deployment's vaults until all of them have migrated (§6.2).
- **A migration sequence fails part-way.** Each migration commits on its own, so a failure leaves a vault at a schema the previous code refuses. The barrier stays until the owner aborts (the pre-upgrade snapshots restored into new directories, the pins switched) or repairs forward with a fixed tag (§6.2, G10).
- **The sanitized head fixture keeps the shape of six attempts** (items, grades, times), though none of the owner's words. The owner approves that in S0, or the fixture leaves with its tests in the owner lane until S3 (§7.2).
- **A database and files from different moments.** A restore uses only whole snapshots, whose database and files were taken at one quiesced point and are checked against one manifest; continuous replication of the database alone is deferred (§11). Recovery after a restore keeps a file that matches neither side of a pending intent and reports the conflict instead of overwriting it (§6.7, G11).
- **Environment skew.** Work the desktop submits runs with the hub service's routes and extras, not the desktop's; doctor and Settings show the primary's (§6.2, G12).
- **The tip stays exposed while S0 waits.** The owner deferred S0 (2026-10-14), so the databases, book text and third-party files of §3.3 stay downloadable from the tip until the owner triggers it. S1 moves the live vaults out of the checkout, so no new learning history is added meanwhile; agents still never commit changes to the tracked working vaults (CLAUDE.md), and S3, if it lands first, adds only sanitized or synthetic fixtures (§7.2).
- **Stale pins after a rename.** A desktop whose remembered vault was moved opens another vault without saying so; the S0-first path re-points every pin at once (§7.1 step 6).
- **History stays public** under H3, and in the fork and every clone under every option; only the owner can choose (§7.4).
- **Kept samples carry their own licences.** A non-commercial sample binds whoever redistributes it; D16 keeps them few, optional and labelled.
- **Contributed traces can identify a learner.** One person's pseudonymous trace, timing and reading list can be enough; consent says so, redaction is the default, and S9 waits for its triggers (§6.12).
- **Time zones.** A travelling learner sees the hub's day (§6.6).
- **Projects capture on the laptop.** The project-understanding hook writes to a local path (§2.5), so commits in repositories on the laptop are not captured until an upload path exists (§11).
