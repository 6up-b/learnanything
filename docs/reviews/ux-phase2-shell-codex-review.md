### What changed, per finding

- **F1.** `SqliteBrowser` gains `editGate`. With it, an *allow edits* switch (off each time Data opens) gates every write path: the cell editor (Enter, `i`, `e`, double-click, the inspector's *edit*), *+ row*, each row's ✕ and the SQL console, which is replaced by a one-line read-only note. Each write function also refuses while edits are off. A SQL statement can write, so the console waits behind the switch as a whole. Classifying statements as reads in the client would be fragile (`WITH … DELETE`, `PRAGMA x=…`). `DataTool` mounts the browser with the gate. In the simple shell `LibraryScreen` (the Library's *Notes & files* and Under the hood → *Files*) filters `.sqlite`/`.sqlite3`/`.db` files and their `-wal`/`-shm`/`-journal` out of the tree (`learnerTree`), so the database is reached only through Data (spec Q18). Lock files stay listed; Q18 names the database only. Classic's tree and its Library SQLite view are unchanged. This answers the stage's open question Q3 with the spec's accepted default.
- **F2.** `addNotice` no longer caps the list. `visibleNotices` draws at most `MAX_VISIBLE_NOTICES` (3) rows in list order: errors first, oldest first, then notices in the rows left (none while held). The rest wait in the list. Dedupe of a repeated message is unchanged.
- **F3.** `errors.ts` gains `ErrorReport {error?, retry?}` and `ReportError`. `App.onError(message, report?)` reads the code and `retryable` from the rejection and offers *Try again* only when both the retryable flag and a retry are there. Classic shows the sentence as before. Wired for the two read-load surfaces that reported a bare `loadError.message`: `KnowledgeMapView` (Analyst views, also Progress's knowledge field) and `LibraryScreen` (Files, Notes & files). Each retry refetches the failed query; a retry that fails again comes back as a new error, never an unhandled rejection (vitest caught that on the first cut). **Not wired:** screen *write* failures (SqliteBrowser's edits, the calibration start, the screens' own submit paths) still pass a sentence. None of them carries an idempotency key through `onError`. Retrying a write whose first attempt may have landed (a sidecar timeout) could repeat it, which is exactly what the finding warns about. They keep their screens' own controls. `ErrorReport`'s doc states the rule (a write's retry must pass the original idempotency key) for any later wiring. The shell's own three retries (`reportError`) are unchanged.
- **F4.** An effect on `open` (simple shell only) resets the line, cursor, history index and selection, so every opening starts on the plain commands. Within one opening the shell still stays after a `>` command, with its output on screen.
- **F5.** The palette command, in the Reader with a book open, increments `readerAskRequest`. `ReaderScreen` gains an optional `askRequest` prop. Each new value expands the rail, selects *Ask* and focuses its box; the value it mounts with does nothing, so a remount never reopens Ask, and no question is sent. Elsewhere the command is as before ("Nothing here to ask about…" when there is no context). `ReaderScreen.tsx` changes only by this prop and one effect. It is the nav integration the finding needs, and it merges cleanly beside the parallel Reader stages.
- **F6.** The writer, not the display. `persist_unknown_error_type_proposals` now calls `persist_proposal_batch(..., join_pending=attempt_ref)`. With `join_pending`, the batch insert takes `BEGIN IMMEDIATE` (unless the caller's transaction already holds it), then checks each item for a `pending` item of the same `item_type` and `client_item_id`. Items that already wait are not written again: the attempt's ref joins that item's batch's `source_refs_json` (once; a regrade of the same attempt adds nothing), and only the rest are written as a new batch. A rejected or accepted proposal absorbs nothing, so a later grading proposes the type afresh, as before. Proposal tables are `WORKFLOW` in `table_roles.py`: no replayer rebuilds them, and no grading, scheduling, evidence or projection path reads them, so there is **no algorithm successor**. Other callers of `persist_proposal_batch` don't pass `join_pending` and behave exactly as before. The first cut (`05f21f302`) put this in a second repository method around a private insert helper. The regenerated DB reference then credited `proposed_patches`' writes to the helper and dropped the external callers from its writer lists, so `579d0512b` moved the check back inside `persist_proposal_batch`, with the same behaviour and tests. Proposals already duplicated in a vault stay; the simple shell's *proposed n×* / *repeat* marks still show them. This resolves the stage's open question Q4 and its open item.
- **F7.** `restartHidden(list, visibleIds)` clears the stamp of any notice that has left the screen unexpired (held in the Reader, or pushed off by an error). `NoticeHost` runs it whenever a stamped notice is off screen, so a returning notice gets its whole time. Errors keep their stamp; they never expire.
- **F8.** `SqliteBrowser`'s grid handler returns early on Ctrl, Meta or Alt, so a modified key is never a grid key. Ctrl+K reaches the palette, and the shell's other chords pass through. The key map's claim (the Reader workbench's Ctrl+K is the one scoped override) now holds. This also applies wherever the browser mounts, classic included: there Ctrl+arrow no longer moves the cell (plain arrows and `hjkl` do).
- **F9.** `parameter_registry.py` gains an exact rule for `ui.shell`: structural, operational, display only, read by the app snapshot alone, no successor.
