## G3-1: an exposed probe answer updates no belief in its episode

- **Before (mvp-0.60 and below).** The episode observation's contamination test looked only at hints, tutor help and the attempt type. A probe answer given after its feedback was shown ("Show anyway", or feedback released before a wait), after its causes were displayed, or after a reveal in its learning object counted at full weight (`independent_evidence_discount` 1.0) and qualified for completion, while the discriminating observation refused the same answer as not independent.
- **At mvp-0.61.** One exposure test, two callers: `probe_episodes.probe_answer_admissibility` (moved out of `causal_discrimination`, so the episode reader does not import the discrimination module, which put it in an import cycle; it imports `attempts.reveal_ledger` at module level, so the frozen inventory of function-local cross-domain edges loses `causal_discrimination`'s entry and gains none) is what the discriminating observation calls and what the episode calls through `probe_episodes.answer_exposure`. An exposed answer takes the held grade's shape: `updates_belief` false, `independent_evidence_discount` 0.0, never qualifying, its reason recorded as `answer_exposed` with what the exposure test gave (`probe_evidence._presentation_contamination`). The live writer (`probe_evidence._record_presentation_observation`) writes `posterior_after` equal to `posterior_before` and a realized information gain of 0. An answer both hinted or tutored and exposed is exposed (no update). Why no update rather than a damped one: the instrument's likelihoods are for an answer produced cold; once the feedback, the causes or a reveal were shown, the outcome no longer separates the causes, and the discriminating observation already refuses the same answer as not independent, so the two records now agree in full. The first round's damped reading (at `probe.episode.contaminated_evidence_weight`, 0.3) is gone with its helper `exposed_evidence_weight`.
- **Stored history.** `probe_observations` is a raw ledger, so a stored row is never rewritten. `probe_episodes.effective_episode_observations` reads it through the same test at the vault's tag (the held-grade view's pattern: `updates_belief` and `eligible_for_completion` false, discount 0.0, the joined raw columns too; the stored posteriors are left as they are, as the held-grade view leaves a held row's), and every reader of the flags that has the vault uses it: `episode_posterior` (posterior and qualifying count; instructional valuation reads that posterior), `probe_completion.evaluate_completion`, `robust_gate_counterfactual`, `_robust_gate_verdict`, `probe_blocks.block_complete`, `calibration_sessions.calibration_session_progress`, and the value receipt's episode-maximum count (`voi_stopping.probe_episode_decision` takes it from its four callers as `qualifying_observations`, through `probe_episodes.qualifying_observation_count`, so the value module does not import the episode reader; that import merged two import cycles). A live observation at the tag is written already exposed, so live and stored read alike.
- **Readers of `updates_belief` checked for a live row with it false** (the held-grade path is the precedent: a held grade is written exactly so). `probe_episodes.episode_posterior` skips its update (as for a held grade). `probe_audit.replay_determinism_report` (the audit report) reads the stored row: for a live exposed row its entropy and posterior checks hold (after equals before) and the transition check is skipped (`not updates_belief`); a stored row below the tag keeps its full-weight transition, which the audit recomputes from its stored discount 1.0, so it stays consistent. `diagnostic_pack._baseline_evidence_projection` (no vault, stored rows) counts a row with `updates_belief` false as quarantined, so a live exposed answer at the tag labels its cell `contested` when nothing clean touches it, where the first round's damped row was a pass or a fail; a stored row below the tag is read as before. `learnloop_sidecar.handlers.inspector` only displays the flag. `adaptive_difficulty.column_classes` only classifies the column. Every completion reader reads `eligible_for_completion`, false either way. Left on the row as written: `grader_channel.observed_outcome` and the robust snapshot (`features.robust`, whose `posterior_after` no code reads; the EVSI live report reads its realized emission and `observed_outcome` as what was observed, which stays true of an exposed answer); the probe grade's dual write to the grade channel (a grade, not a belief). Nothing feeds `record_real_observation_counts`, which runs only for a qualifying answer.
- **Left as they were.** The exposure does not change the attempt's activity class (`causal_activity_classification_events`) and does not close the diagnostic segment: a read cannot close a segment, so a live write does not either, and live and stored stay equal. Two readers still count stored flags: the per-session cap (`Repository.qualifying_probe_observation_count_for_session`, which has no vault; only a session open across the upgrade could see an old exposed answer) and the golden-path assessment's baseline projection above. Both see the right flags for answers recorded at the tag.
- **Who sees what move.** A belief about a cause (the episode posterior, and the misconception marginals persisted from it at the next episode update), a choice of repair (instructional valuation reads that posterior), the value-of-information stop (it reads that posterior), an episode's completion (an exposed answer no longer counts toward breadth or the cap). On the owner's arxiv vault the orchestrator's comparison found three such answers in four.
- **Fail-first.** `tests/test_evidence_reading_successor.py::test_g3_1_an_exposed_probe_answer_updates_no_belief_in_its_episode[mvp-0.61-shown_anyway-…]` and `[mvp-0.61-reveal-…]`, `::test_g3_1_a_hinted_answer_that_was_also_exposed_is_exposed[mvp-0.61]`, and `::test_g3_1_an_exposed_answer_recorded_below_the_tag_updates_no_belief_after_the_upgrade[…]` (both exposures): against the first round's code (the damped reading) all five failed (`0.3 == 0.0`, `(0.3, True) == (0.0, False)`); all pass after. In the first round, with `answer_exposure` forced to None, the exposure tests failed too. The probe answers are model-graded (an approved source; the journeys' self-graded probes write no episode observation) and the post-attempt pipeline writes the discriminating observation, whose refusal reason each test checks.
- **The instrument in the tests.** The journey's generated probe reads every outcome alike for its two causes (its likelihoods are flat: a stored observation's `posterior_after` equals its `posterior_before` even at full weight below the tag), so no belief update could be seen with it. The G3-1 tests install `_DiscriminatingInstrument`, which makes `instrument_observation_likelihoods` separate the causes in both the live writer and the episode reader alike (and can be set flat, to give "the episode without what the answer says"). The first round's "moves no further than the full weight" check held trivially for that reason.
- **Both tags.** The same tests' `[mvp-0.60-…]` arms pin today's result (no contamination, discount 1.0, `updates_belief` true, qualifying, and the posterior moved; for the hinted answer, damped to the contaminated weight and still updating). `::test_g3_1_a_clean_probe_answer_is_unchanged_at_the_tag` is the control. ## ER-2: an unassessed criterion row is no assessed zero to diagnosis

- **Before.** A row the own-route rule or PF-c marks unassessed was read by trace consistency as a checked, held claim (`consistent_with_claims`) and by the criterion receipt as an assessable, failed criterion.
- **At mvp-0.61.** `causal_attribution._unassessed_criteria` (the tag's gate over `canonical_projection.unassessed_evidence_row`) feeds both readers: trace consistency leaves the criterion out of the awarded scores (a claim about it is `unknown`, `claim_criteria_were_not_assessed`); the criterion receipt gives it no localization outcome (as the canonical projection: a missing dependency reads as passed, so it neither fails nor blocks its descendants) and marks its row not assessable, not passed, no full credit.

## K5-8: the forgetting clock (variant requests at the tag; probe approval live; the rest checked)

The owner's rule (2026-11-18): a skip leaves the forgetting clock alone; an answered attempt that gets no review (hinted-ineligible, primed, a probe, a held grade) restarts the clock and keeps the due date. The clock is `PracticeItemState.last_attempt_at`. The inventory is `docs/reviews/refactor-k5-fixes-2.md` ("K5-8 · Forgetting clock inventory"); its line numbers are from before this branch. Each case:

### Case A: a request for an easier or harder variant (at the tag)

- **Before (mvp-0.60 and below).** `content/authoring/rung_variants.request_rung_variant` records the request as a deterministic self-graded `self_report` attempt on the source item (its belief write: 0.3 evidence mass, LO mastery, facet recall, the (facet, capability) ledger). As an unprimed self-report it was also an FSRS review of the source item (easier: a soft failure; harder: a success), which set the item's memory state and due date and restarted its clock although the learner answered nothing; replay did the same.
- **At mvp-0.61.** The request keeps its belief write, unchanged, and applies no FSRS review: the source item's `last_attempt_at`, stability, difficulty, retrievability and due date stay exactly as they were (the stored row is written back as it was, its `updated_at` aside; an item with no row yet gets one with nothing in it), live and on replay. The decision record says `skipped: "variant_request"`. Code: `GradeInputs.variant_request`, set in `_compute_resolved_grade_application` from `replay_reading.withholds_review_as_variant_request` (false below the tag); `attempts._fsrs_review` skips the review on it; `attempts.grade_application` keeps the prior item state on it.
- **Recognition is structural, one rule live and on replay**: the `rung_variant_requests` row whose `attempt_id` names the attempt (`Repository.rung_variant_request_for_attempt`, new), never the answer text or `entry_surface` (old rows carry `unknown`). So that the live write sees the row too, `request_rung_variant` now draws the attempt id itself, writes it on the request row, then applies the attempt (`complete_self_graded_attempt` takes an optional `attempt_id`); before, the id was written after the attempt. The id is drawn at the same point of the id stream as before (nothing draws an id between). Below the tag the row is written in the new order but nothing reads it, so a vault at mvp-0.60 records and rebuilds as before.
- **Stored request rows without the attempt id.** `update_rung_variant_request(attempt_id=…)` ran right after the attempt was applied, outside its transaction, so a process that died between the two left an attempt no request row names. Such an attempt keeps today's behaviour at the tag (a review of its source item), live history and rebuild alike. A request whose attempt failed to apply never had an attempt. (The best-effort `rung_variant_requested` interaction event also carries the attempt id; it is not read, being best-effort.) From this branch, a request whose attempt fails to apply leaves a pending row naming an attempt that does not exist, where before it named none; no reader joins on it.
- **Other self-reports are not touched**: an ordinary `self_report` with no request row is still a review at both tags.
- **Who sees what move.** The source item of every stored variant request: on the upgrade's rebuild its memory state and due date are recomputed without those reviews, and its clock goes back to the answer before the request; with them the due queue, the router objective's recall reads and the learner counts that read the clock or the due date (inventory's reader table). The request's belief write does not move.
- **Fail-first.** `tests/test_evidence_reading_successor.py::test_k5_8_a_variant_request_is_no_review_of_its_source_item[mvp-0.61]`: with `withholds_review_as_variant_request` forced false (the code before the change) it failed (the day-4 request was a review, elapsed 4.0 then 3.0); with the request row named after the attempt (the old write order) it failed on `live == rebuilt` (live reviewed, the rebuild did not). Passes after.
- **Both tags.** The same test: day 0 an answer, day 4 a request for an easier variant, day 7 an answer, against the same history without the request, live and after a rebuild. At mvp-0.61 the reviews' inputs (memory before, rating, elapsed days: 0 then 7) and the item's state equal those without the request; at mvp-0.60 they are today's (elapsed 0, 4, 3; a different state). Live equals rebuilt at both tags. `::test_k5_8_an_ordinary_self_report_is_still_a_review[…]` is the control (elapsed 0, 4, 3 at both tags). `::test_k5_8_a_variant_request_writes_the_same_belief_at_both_tags`: the attempt row, the learning object's mastery and the facet recall rows after a harder request are equal at both tags.

### Case B: a quarantined answer, or one ineligible before its response (checked; nothing built)

- **What the inventory said.** On replay, `attempts.py` derives review eligibility from fixed practice/no-feedback inputs and does not read a stored quarantine or before-response eligibility, so an answer that got no review live could get one on a rebuild.
- **What I found.** No stored fact says "this answer got no review live" for either reason, and live and replay already agree. The live attempt path derives eligibility from the same fixed inputs (`attempts._fsrs_review`: `evidence_eligibility_for(purpose="practice", feedback_condition=None)`), so every answer the attempt path records gets a `practice`-eligible observation and is reviewed by the same rules on both sides; no practice answer's observation carries a before-response condition (the only before-response writer, the golden-path assessment, records an assessment observation and no practice attempt or item state). A quarantine (`grade_resolution.quarantine_observation`, which no production path calls today; the tests and the grading CLI's tests do) appends an interpretation to the grade channel after the answer was reviewed at submission, so replay reviewing it again is what happened live. An answer that got no review live for any other reason (held, primed, a probe, hinted-ineligible) is replayed from its recorded flags, as the first round's day-4 regressions showed.
- **Decision.** Not built: there is nothing for replay to honour, and honouring a later quarantine would change history that live applied. `tests/test_evidence_reading_successor.py::test_k5_8_a_quarantined_answer_kept_its_review_live_and_keeps_it_on_replay[…]` pins the agreement at both tags (day 0, a day-4 answer quarantined on day 5, day 7: reviews at elapsed 0, 4, 3 and the item's state equal live and after a rebuild; the quarantined answer's observation is `practice`). It passed before any change (it is a characterization, not a fail-first test). The ledger's wording for this case is left to the orchestrator.

### Case C: approving a probe instance that was already answered (live, no tag)

- **Before.** `diagnosis/probe_instance_generation.approve_probe_instance` activated the instance with the generic `upsert_practice_item_state(id, active=True)`, which replaces the whole row on conflict, so approving an instance that had been answered cleared its clock, memory state and due date with no answer behind them.
- **After.** It calls the existing activation-only `Repository.set_practice_item_active` (an UPDATE of `active` and `updated_at`; a fresh row when none exists, as before). No tag: a rebuild already replays the attempt and restores the state, so this makes the live row equal to the rebuilt one; the test checks that the rebuilt row has the same clock and memory and is active too, so the fix moves nothing a rebuild derives.
- **Fail-first.** `tests/test_probe_instance_generation.py::test_approving_an_answered_probe_keeps_its_scheduling_state` failed before (`last_attempt_at` None != the answer's time) and passes after. Its probe is answered as a diagnostic probe, so its memory and due were empty to begin with; the clock is what the old write lost.

### Kept by design (comments only)

- A blank submission stays a recorded retrieval failure, like a declared stuck or don't-know: the learner submitted and saw the feedback, and the review is rated from a zero. `attempts._attempt_manual_review_reason` flags it for a person (`blank_answer`) and withholds nothing; a comment there now says so. The inventory's "Fits owner rule: **No**" for blank submissions read the blank as no answer; under the owner's rule it is an answered attempt (the desktop's empty submit is the declared-stuck path). No comment in the code said otherwise.
- A score-only exam import with a zero keeps its review on the exam date (`goals/exam_seeding`: the receipt cannot tell a question left blank from one answered wrong); comment added.
- Exam answers restart their items' clocks and get their reviews when the sitting finishes, not at submission (`goals/exam_session.finish_exam`; a staged answer writes no item state, so an unfinished sitting moves no clock); comment added.

## Judgment calls (read these first)

1. **What an exposed answer becomes (G3-1, second round).** No belief update at all, the held grade's shape (`updates_belief` false, discount 0.0, never qualifying), at the orchestrator's direction after the first round offered it as the alternative to the damped reading. Kept on the exposed row: the observed outcome and the robust snapshot (what was observed, read as realized emissions by the EVSI live report; the snapshot's own `posterior_after` is read by nothing) and the probe grade's dual write. The effective view leaves a stored row's posteriors as they are (the held-grade view's precedent), so the readers of a stored row's `posterior_after` (`probe_audit`'s determinism report, which checks the receipt against itself, and its replication count over qualifying rows, which reads the stored flag) see the receipt. The golden-path baseline projection, which reads stored flags without the vault, now counts a live exposed answer as quarantined (`contested`), not a pass or fail. The exposure still leaves the attempt's activity class and the state segment alone, so that a live write and a read of a stored row agree.
2. **Which stamps say v2 (K5-3).** Only the outcome row, where the verdict is recorded, and only at the tag. Bumping every use of the constant would stamp v2 on vaults below the tag and re-key a measurement opportunity for every learning object at the upgrade (the opportunity's trigger key carries the version); what counts as held out and when a probe is due did not change, so the scheduling stamps keep `certification_cold_probe_policy_v1` (`COLD_PROBE_POLICY_VERSION_V1`). The abstention reason is `grade_unavailable`, the only fitting one migration 139's CHECK allows.
3. **What K5-11 and K5-12 can and cannot repair.** The source rule moves only attempts whose recorded source is `self` or `deterministic` and whose current epoch a different model run wrote; a model regrade of a model grade keeps the first source (a run's provider column can be a default, not a name, as a test fake showed). The run's source comes from its `agent_runs.provider` by the regrade door's own name split, so an AI route served by a Codex-named provider reads `codex`. The exam replacement takes that source too rather than the exam path's fixed `codex`. And a 0.0 confidence an earlier rebuild or regrade replay already overwrote on the attempt row stays 1.0: the fix as specified stops further loss, it does not read the first raw grade event back.

4. **How a variant request is recognized (K5-8 A).** By its request row naming the attempt, the same rule live and on replay, which needed the request row written before the attempt is applied (the attempt id drawn by `request_rung_variant`). The alternative, a flag passed down the live call chain with the row read only on replay, would have been two rules for one fact. What this costs: a request whose attempt fails to apply leaves a pending row naming an attempt that never existed (it named none before; nothing joins on it), and one indexless lookup of `rung_variant_requests` per applied attempt (the table holds one row per request). The module's docstring had called the source item's FSRS move "owner-approved"; it now says what the tag does. If that approval still stands for some case, this change reverses it, so the owner should read it.
5. **What "exactly as they were" keeps (K5-8 A).** The stored item row is written back whole (`replace(previous, updated_at=now)`): clock, memory (retrievability included), due date, `active` and `content_hash` as stored, rather than the normal path's recomputed `active`/`content_hash`. An item with no state row gets a row with no memory, no due date and no clock. `scheduling/review_log.py` (the FSRS fitting reader, which reconstructs elapsed days from successive attempts and excludes only held grades) is not changed: it still counts a variant request as a review for fitting, as it already counts primed answers and probes (the inventory's reader table).
6. **The quarantine case is not built (K5-8 B).** Live and replay already agree; see the case. A rule that a later quarantine withdraws a review would change history live applied, and needs its own decision.
7. **The structure ratchet.** `attempts.py`'s line ratchet rose 5814 → 5820 in `bee57a7a9e` (the flag, its read, the kept state, the attempt id parameter; the request's recognition itself lives in `replay_reading`); `6b53ee15f9` took it to 5818 (the blank-answer condition on one line), and the golden was left at 5820. Only that line was edited: `tests/test_structure_ratchets.py --write` also rewrites members that drifted before this branch (`reader.py` 2979 → 2970 and four files' stage-comment counts), which are not this change's.
