## D-32: the teach-back sim on a split vault

**Failing test.** `tests/test_sim_teach_back.py` with its `append_config_toml(root, "[diagnosis]\nsplit_enabled = false")` removed: at the base, `test_runner_completes_session_with_teach_back_item` errored in the module fixture with `AIProviderUnavailable: AI provider 'simulator' cannot isolate structured operation 'blind_grading' from files, tools and the vault` (`ai/transport.py:209`). Every vault grades blind by default, so `learnloop sim` failed on any teach-back item.

**Fix.** Of the brief's two choices, the simulator client offers the isolated operation (`sim/runner.py`, `_SimTeachBackClient`): `supports` declares `ISOLATED_TURN` beside `STRUCTURED_COMPLETION`, and `complete` answers `blind_grading` (result model `BlindGradingProposal`) with the same synthetic points as the joint `grading` operation, through one shared `_criterion_grades`. The comment says what the production check protects against (an agentic model reading prior grades and diagnoses from the vault's files, a shell, the network or its tools) and why the client is isolated by construction (it reads nothing but the request's prompt and the synthetic student's points). Why this one and not a door of the sim's own: the sim then runs the production teach-back path unchanged (`finish_teach_back` -> `request_vault_grading_proposal` -> `request_blind_grading_proposal` -> `to_grading_proposal` and the blind identity on the agent run and raw grade), so a split vault's simulated teach-back is graded the way a real one is; a separate door would test a path no vault takes. `execute_structured_operation`'s check and every real provider's `supports` are unchanged (the diff touches neither).

**Tests.** The switch line is gone (no `tests/test_sim_*` file sets the split off now). `test_a_split_vault_grades_the_simulated_teach_back_blind`: the run's vault is split and the teach-back's grading run is recorded with `output_schema = BlindGradingProposal`. `test_a_provider_that_cannot_isolate_is_still_refused_the_blind_grader`: a structured provider double that declares no isolated turn is refused by `request_vault_grading_proposal` on the split vault (`cannot isolate structured operation 'blind_grading'`) and is never sent the request. The existing assertions (the simulator named as the provider, seed determinism, the sweep) pass unchanged on the blind path.

**Callers and siblings.** `_SimTeachBackClient` is the only AI client in `src/learnloop/sim/` and `src/learnloop/evsi_calibration/` (no other `supports`, `provider_name` or structured operation there). It is called by `next_question` (`teach_back`) and `finish_teach_back` (`grading` or `blind_grading`); any other purpose still raises. The production isolated callers (`ops/pf_calls.py`, `figures/routes.py`, `diagnosis/grading_hardcases.py`, `diagnosis/offline_review/runner.py`, `content/proposals/method_phrasing.py`, `daily_plan/router_runtime.py`) ask their own clients; none receives the sim's. `diagnosis.split_enabled` stays (another step removes it).

**Not verified.** The `blind_grading` answer for a context with a PF-c reference policy or a stuck prompt (other result models): `request_vault_grading_proposal` builds neither, and the client raises on them rather than guessing a shape.

## D-41: an empty report passed

**Failing tests** (`tests/test_sim_probe_validation_cli.py`, at the base): `ValidationReport().passes(...)` was true; `sim probe-validation --seeds 1 --planted unfamiliar` on a default `create_basic_vault` printed `Overall: label 0.00, action 0.00 — PASS` and exited 0; `sim probe-pilot` printed `Entry gate (Checkpoint 3 sim validation): PASS` and exited 0; the report had no `refusal` field.

**Can the sim set up its own episode on a default vault?** No, not honestly: FG1 (`followup.generate_and_serve`) has a model write the episode's probes and mints no parametric instance (`probe_instance_generation.py`, the `if not fg1` branch), and the sim calls no model, so with FG1 on its episode has nothing to serve whatever opens it. With placement on (`placement.enabled`), state sync opens no opening episode (`initial_probes_enabled`), and the opening episode with its cold-start claim is what the simulation measures; a default vault never runs that episode on a new learning object, so opening it by hand would simulate something the vault does not do. So the sim refuses, and says these are its limits, not the vault's.

**Fix.**
- `sim/diagnostic_validation.py`: `simulation_refusal(vault)` names the switches on (after the run's overrides) that leave the simulation nothing to run, each with its reason; `run_probe_validation` returns a report with `refusal` set and no results before any episode when it is not None (every run copies the same vault under the same overrides). A run that opens no episode for another reason is listed in `not_run` with why (no open episode after sync, none on the named `--lo`, or the episode gone after generation), instead of being dropped silently. `passes()` is false with a refusal, a run not run, or no results. `as_dict()` carries `refusal` (switches, reasons, message) and `not_run`.
- `cli/sim.py`: both commands print the refusal ("... This is the simulation's limit, not the vault's: it needs placement.enabled = false, followup.generate_and_serve = false on its run copies (the vault itself is never written).", then the `--set` flags to rerun with) and `FAIL: no episode ran.`, and exit 1, before any accuracy line; runs not run are listed. With `--json` (and no `--output`) a failing gate now exits 1 too (it returned 0 before, whatever the gate said): the brief's "the JSON output carries the same". `probe-pilot` audits no run vault when nothing ran (a refused run leaves one untouched copy).

**Callers and siblings.** `run_probe_validation` and `passes()`: the two commands (both fixed), `tests/test_sim_probe_validation.py`, `tests/test_sim_planted_types_forty_seeds.py`, `tests/test_robust_completion_gate.py`, `tests/test_ux_phase4_feedback.py::test_f1l_...` (all build the helper's vault with the two switches off, so none is refused; all pass). The same exit-0-on-FAIL defect in the `--json` path of both commands is fixed here. Other gates in the sims answering "did it pass": `sim/kinship_admission.KinshipAdmissionReport.no_decision_flip` is `all()` over a grid `run_admission_sim` always fills with at least two points (not empty by construction); `evsi_calibration/compare._all` already returns None on an empty list. No other `passes` in `sim/` or `evsi_calibration/`.

**Assertion changed.** `test_sim_probe_validation.py::test_every_planted_episode_completes_within_its_budget`: the comment about the empty report replaced, and it now also asserts `refusal is None and not_run == []` (stricter).

**Not verified.** The CLI's text output was checked through `CliRunner` only (no run in a terminal). A vault with `placement.initial_probes = true` (placement on, opening episodes kept) is not refused by construction (`initial_probes_enabled`); not run.

## D-42: a seed did not fix a run

**Failing test.** `tests/test_sim_probe_validation.py::test_a_seed_fixes_the_run[gate_decides]` and `[value_decides]`: two runs of one (type, seed) compared with ULIDs masked. At the base both failed on the ensembles' numbers, not only the ids (gate: `lcb_advantage_over_runner_up` and the likelihood ensembles in the logged gate decisions; value: `evsi_robust_minutes` and the other forecasts in the completion detail).

**How ids are minted.** `probe_episodes.enter_episode` mints `episode_id = new_ulid()` (called from state sync's `_enter_initial_probes`); `probe_robust.instrument_ensemble` puts it in `decision_context_hash`, which seeds `build_ensemble`. `new_ulid` is the wall clock's millisecond plus `secrets.randbits(80)` under a process-wide monotonic rule. Nothing lets a caller supply the episode id, and `src/learnloop/diagnosis/` is out of scope; changing what the ensemble seeds on is a stored-seed change. Neither was done.

**Fix (sim only).** `diagnostic_validation.seeded_ulids(seed, start)`: for the duration of one planted run, `learnloop.ids`'s own stream has its timestamp pinned to the run's start (`VALIDATION_START`), its randomness drawn from `random.Random(f"probe-validation-ids|{seed}")` and its monotonic state started afresh; the previous clock, randomness source and state come back afterwards (under the module's lock), so ids minted later in the process still sort after those minted before. Every `new_ulid` of the run is then fixed (the episode's, its presentations', its attempts') and still sorts in creation order. It is the pinning the suite already uses for ids (`tests/test_due_queue_golden.py`, `tests/test_arcb_close_fixes.py`, `tests/test_ids.py` patch the same three names), applied by the sim to its own runs; production defaults are untouched and an episode in a vault still seeds on its own id. The seed is the run's seed alone, so two planted types at one seed share ensembles (common random numbers across types; each run is its own vault copy). The module docstring now says a seed fixes the run.

**Proof.** `test_a_seed_fixes_the_run` runs every planted type at seed 11 twice in each configuration the planted suite uses (the gate deciding, value deciding) and compares the results and every stored record (completion detail, logged gate decisions) masked and then byte for byte: equal. Mutation (not committed): with the context manager replaced by `nullcontext`, both cases fail again.

**The forty-seed rates.** `tests/test_sim_planted_types_forty_seeds.py` (the gate deciding), now fixed numbers, recorded in its docstring with its threshold kept at 26: named and acted on correctly in 39, 37, 32, 30 and 33 of 40 (robust_initial_grasp, unfamiliar, surface_only, schema_without_transfer, confuses_with), every episode `observation_budget_exhausted` at 4 probes, 0 of 200 abstaining. These equal K9.0b's measured numbers: in this configuration every episode runs to its budget, so the ensembles' seed never changed an outcome there, only the logged numbers. Read off with a scratch pytest plugin wrapping `_run_one_episode` (outside the checkout, not committed); the file ran twice and the 200 runs were identical, episode ids included (5 passed each time, about 12 s at `-n 5`, not the 17 minutes the brief expected). Where value decides (K9.0b's moving case, `unfamiliar`, 40 seeds, a scratch script through the wrapper): two runs identical, 37 of 40 named, every episode `value_of_information_stop`, probes 1 (36), 2 (1), 3 (3).

**Callers and siblings.** `decision_context_hash` callers: `probe_robust` (the episode id: this row), `attempts/effective_observation` and `sim/grader_confusion` (both `episode_id=None`, deterministic already). `sim/runner.run_simulation` (the general sim) is not wrapped: its report-level determinism is tested with ULIDs stripped (`deterministic_dict`), and whether its runs reach a robust episode decision, and how the router's own id stream (`ids.UlidStream`, system randomness) bears on it, was not measured. Not a reproduced defect, so no ledger row; an open item below.

**Limits.** One run at a time in a process: a thread minting ids during a run would draw from the run's stream and shift it (the docstring says so). The CLI and the tests run one at a time.

## D-44: the EVSI sim's incumbent gate

**Failing test.** `tests/test_evsi_calibration_sim.py::test_the_incumbent_goes_on_past_a_fragile_pick_as_serving_does`: two informative instruments a hair apart (distinct ensembles), a uniform belief over three hypotheses that route to three repairs, at the minimum independent observations, where `evaluate_selection` abstains with `should_stop` false. At the base, `P.decide("incumbent", state, PolicySettings(draw_count=8))` returned `Decision(action='stop', verdict='stop', reason='couldnt_reliably_distinguish')` (shown with a scratch script on the same state; the test itself failed first on the missing setting).

**Fix.** `PolicySettings.robust_gate_fixes: bool = True` (named for serving's `probe.episode.robust_gate_fixes`). `_robust_gate_abstains` became `_robust_gate_ends`: `evaluate_selection(..., distinct_instruments=settings.robust_gate_fixes)` and production's own `probe_episodes.robust_gate_completion(decision, stop_only=settings.robust_gate_fixes)`, so the sim cannot drift from serving's rule. True is mvp-0.59 serving (only a fragile stop ends the episode; identical ensembles counted once, inert in the studies' own runs where each question seeds on its own id); false is the predecessor exactly (the code before this commit). The module docstring says which gate `incumbent` mirrors and that the recorded studies ran the predecessor. The three study records (`docs/reviews/evsi-calibration.md`, `evsi-single-family-unbounded.md`, `evsi-multisim.md`) carry a label under their titles: their `incumbent` numbers (and the multi-family study's `voi_successor` and `voi_p_with_gate`) ran the mvp-0.58 gate, `robust_gate_fixes = False` selects it, not rerun. No study was regenerated; `tests/evsi_calibration_claims_v2.json` (a stored v2 report the single-family tests read) is unchanged.

**Tests.** The fail-first above also asserts `_incumbent_stop(..., budget=False)` is None (the successor's path). `test_the_predecessor_gate_stops_on_a_fragile_pick`: with `robust_gate_fixes=False` the same state stops `couldnt_reliably_distinguish`.

**Assertion changed.** `test_the_incumbent_arm_includes_todays_robust_completion_gate` (review F8 of the EVSI stage) is renamed `test_the_incumbent_arm_includes_the_robust_completion_gate`; its assertions are unchanged but run under `PolicySettings(draw_count=8, robust_gate_fixes=False)`: they pin the predecessor gate (identical instruments abstain and stop), which is what "today's" meant when it was written. One assertion added: under the default the identical pair is one instrument and the incumbent goes on measuring. Not a loosening: the predecessor's behaviour is still asserted, and the new default has its own assertion.

**Callers and siblings.** `_incumbent_stop` (the only caller of the gate) is used by `decide_capped(robust_gate=True)` (`incumbent`), `decide_successor` (`voi_successor`) and `decide_package(gate=True)` (`voi_p_with_gate`): all three take the setting; `test_evsi_multisim`'s "with all three put back the package IS the successor" still holds decision for decision. `decide_eig` (the `eig` arm) calls `evaluate_selection` as a selection rule, not the completion gate: unchanged. `PolicySettings.as_dict()` now records the field, so a new report's `policy`/`policy_defaults` names its gate; `evsi_calibration/compare` reports the field as changed against an old report (no hash or identity reads it: `test_identity_pins` passes).

**Not verified.** No EVSI study was rerun under the new default, so how the recorded conclusions (for example S3f, the gate's cost of 3.7 minutes at 0.9/30) move is unknown. `learnloop evsi simulate`/`multisim` take no flag for the gate (the predecessor is selectable in code only).
