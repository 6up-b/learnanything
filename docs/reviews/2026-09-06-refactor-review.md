Review of the August refactor, performed September 6, 2026
=======================================================

The domain split and persistence contracts improve maintainability, but I would hold off calling the refactor complete until the recovery and lifecycle issues below are resolved. SQLite remains a good local storage choice; the telemetry needs stronger offer attribution and outcome eligibility before it can support trustworthy learned features. The largest inexpensive performance opportunity I measured is using the existing repository connection-reuse facility on hot local operations. The largest test-efficiency opportunity is reusing prepared fixture templates.

Scope: d0f25b2 → 263a2a7. Runtime changes are in 62fd1f6 and b322ef2; subsequent commits add documentation. The runtime/test diff contains 828 changed files. This is a risk-focused review of changed behavior and its callers, not a claim that every line or learning policy was exhaustively validated. No production code was changed. Fault injections and benchmarks used temporary vault copies.

The [canonical-ingestion follow-up](2026-09-06-ingestion-review.md) incorporates the intended preservation of background work across debug restarts, extends finding 4 with a reproduced late-worker overwrite and a fast-restart lease-recovery gap, and reviews provider interruptions, token budgets, retry costs, prompt caching, and ingestion telemetry. **Findings, ordered by impact**

1. **[P1] A recorded attempt can become permanently stuck in recovery.** [practice.py:608](/home/saturn/Documents/thinking/learnanything/src/learnloop_sidecar/handlers/practice.py:608), [practice.py:632](/home/saturn/Documents/thinking/learnanything/src/learnloop_sidecar/handlers/practice.py:632). The attempt commits before post-attempt processing, result assembly, and receipt persistence. If any of those steps raises or the process dies, every retry encounters the existing attempt and raises submission_committed. Neither recovery nor startup reconstructs the missing receipt or resumes the unfinished work. The new UI offers Retry, so a saved answer can strand the learner indefinitely. This is an incomplete guarantee in the new recovery design, not merely a lost-response problem. Fault injection at run_post_attempt_pipeline produced one durable attempt, no receipt, and the same error on three subsequent recovery calls. Preserve the exact diagnostic routing and no-double-grade safeguards, but persist resumable post-attempt work with the attempt and finish the receipt idempotently. Do not repair this by guessing that feedback may be revealed. The existing test at [test_sidecar_contract.py:615](/home/saturn/Documents/thinking/learnanything/tests/test_sidecar_contract.py:615) explicitly tests refusal after receipt removal, not eventual recovery after interruption.

2. **[Withdrawn as a defect: intended debug-session continuity] Background Python work survives a frontend/sidecar restart.** [sidecar.rs:344](/home/saturn/Documents/thinking/learnanything/apps/learnloop-tauri/src-tauri/src/sidecar.rs:344). The owner clarified that preserving useful in-flight work across app and sidecar restarts within the same session is intended. The observed process survival is therefore not, by itself, a bug or justification for killing the process tree. My original P1 classification and blanket process-tree termination recommendation are withdrawn. The remaining review question is whether surviving work has durable identity, valid ownership, observable progress, and safe reconnection, and whether an expired/replaced worker can overwrite newer work. Finding 4 still applies independently. The canonical-ingestion follow-up reviews those guarantees and token-preserving recovery.

3. **[P1] Failed live rebuilds leave already-cleared learner state published.** [rebuild_orchestrator.py:256](/home/saturn/Documents/thinking/learnanything/src/learnloop/substrate/rebuild_orchestrator.py:256). The new umbrella commits whole-family deletion before calling the replayer. A replay exception leaves those live tables empty without a successful rebuild receipt. In the migration-head fixture, an injected replay failure changed mastery rows from 4 to 0 and surprise rows from 6 to 0; all 6 raw attempts survived, and the rebuild receipt count stayed unchanged. The raw evidence is recoverable, but the app can consume incomplete projections until another successful rebuild. Build and validate candidate projections in scratch state, then publish them atomically against a checked input revision. The live command also needs coordination with concurrent attempt writers; per-family commits and the migration lock alone do not provide that coordination. A whole-operation transaction is another option only after removing internal commits that would break it.

4. **[P2] Lease recovery can overwrite a job that just completed or renewed its lease.** [runner.py:501](/home/saturn/Documents/thinking/learnanything/src/learnloop/content/pipeline/runner.py:501), [ingest_queue.py:418](/home/saturn/Documents/thinking/learnanything/src/learnloop/db/stores/ingest_queue.py:418). Recovery reads expired candidates and later calls an unconditional update by id. Another worker can commit completion or a heartbeat between those operations. A deterministic interleaving using a second repository connection changed a successfully completed job to failed/interrupted while leaving its successful result attached. Downstream work can then become blocked. This race predates the extraction and remains in the new runner/store boundary. Recover with a conditional update that rechecks running status, lease owner, and expiry; propagate failure only if that update actually succeeds. The same ownership fencing should govern late worker completion after retry.

5. **[P2] A completed Reader request does not expose its result while another request is running.** [useReaderRequests.ts:134](/home/saturn/Documents/thinking/learnanything/apps/learnloop-tauri/src/screens/reader/useReaderRequests.ts:134). The extracted hook hydrates artifacts only when no request remains active. With A complete and B still running, A's status updates but its source object and proposal do not. A hook harness executing the actual module observed one artifact fetch on entry, no new fetch when A completed, and a second fetch only when B completed. A slow or stuck B can therefore hide A's finished result. Refresh artifacts when any request newly reaches a terminal state, coalescing simultaneous completions and retaining one in-flight status poll. Test mixed terminal/active states and retry failures.

6. **[P2] The native PDF/media path still waits behind long AI RPCs.** [sidecar.rs:115](/home/saturn/Documents/thinking/learnanything/apps/learnloop-tauri/src-tauri/src/sidecar.rs:115), [main.rs:31](/home/saturn/Documents/thinking/learnanything/apps/learnloop-tauri/src-tauri/src/main.rs:31). resolved_vault_path takes the same mutex that call holds while waiting for a response. Both native resource handlers invoke it, and call_isolated does too. A long grading/tutoring request therefore delays resource delivery and even the start of an allegedly isolated call. This is retained architectural debt. Keep the selected vault identity under a separate short-lived lock, include a vault generation in work that can outlive selection, and use an asynchronous native resource handler for file I/O. Only populate-goal currently takes the isolated CLI path; the architecture documentation overstates how broadly long operations are isolated. Tauri provides an [asynchronous URI-scheme handler](https://docs.rs/tauri/latest/tauri/struct.Builder.html#method.register_asynchronous_uri_scheme_protocol) for responding from separate work.

7. **[P2] Configured manual grading is reported as an unavailable provider.** [context.py:458](/home/saturn/Documents/thinking/learnanything/src/learnloop_sidecar/context.py:458). The resolver now returns a typed manual outcome, but _ai_health only recognizes the runtime override string. A manual route in configuration, or fallback to manual, produces active_provider=manual, ready=false, manual_grading=false. I reproduced that exact response. The desktop consequently presents intentional manual operation as a degraded AI state. Derive the DTO from resolved.manual as well as explicit overrides, with the same contract for both. Also preserve or explicitly refresh the selected grading mode after transport reconnect; the manager currently restores only the vault path.

8. **[P2] A delayed close-listener registration can leak after Practice unmounts.** [PracticeScreen.tsx:395](/home/saturn/Documents/thinking/learnanything/apps/learnloop-tauri/src/screens/PracticeScreen.tsx:395). onCloseRequested returns its disposer asynchronously. If cleanup runs before that promise resolves, cleanup has nothing to call, and the later callback stores a disposer that will never run. The stale listener retains the old draft closure and may race the current screen's save/destroy operation. This is an existing lifecycle gap in code touched by the refactor. Use the disposed-flag pattern already present in App's native event subscription: dispose immediately when registration resolves after unmount. Executing the actual effect with a deferred registration promise reproduced zero disposer calls after cleanup and resolution.

9. **[P2] Logged scheduler propensities describe an intermediate policy, and invalid support can be reported as ready.** [scheduler.py:470](/home/saturn/Documents/thinking/learnanything/src/learnloop/scheduling/scheduler.py:470), [evaluation.py:384](/home/saturn/Documents/thinking/learnanything/src/learnloop/scheduling/evaluation.py:384). Propensities are computed before the teach-back cap, goal quota, requested-item floor, repeat rotation, contrast ordering, and presentation rules. With exploration disabled, the real requested-item floor moves B ahead of A while retaining P(B)=0, although B is now guaranteed to be first. The handler additionally removes unavailable teach-back items after the slate has been persisted ([queue.py:99](/home/saturn/Documents/thinking/learnanything/src/learnloop_sidecar/handlers/queue.py:99)). Those records cannot be interpreted as the probability of the final offer. The evaluation readiness check counts near-one and null propensities but accepts chosen zero-probability candidates: the reproduction reported off_policy_readiness=OK. This is retained telemetry debt, not a new regression from moving the modules. Record the final policy and all eligibility transformations, distinguish inclusion/top-position/user-choice probabilities, and compute design probabilities for the final randomized mechanism. Mark deterministic and unsupported decisions honestly; merely assigning a small positive probability would fabricate support. Add composed-policy tests, including forced floors, filtering, and zero-probability chosen rows.

10. **[P2] An attempt can be attributed to an offer the learner never received.** [repositories.py:17154](/home/saturn/Documents/thinking/learnanything/src/learnloop/db/repositories.py:17154). Ordinary attempts infer their scheduler candidate from the most recent matching item/session before submission. The query does not require was_returned=1, and the ordinary submission contract carries no exact offer identity. If an item is opened from slate A and a refresh produces slate B before submission, the response may acquire B's prediction and context. I persisted A with the item returned, then B with the item considered but excluded, then submitted through complete_self_graded_attempt: the attempt linked to B and its was_returned=false candidate. Even filtering out unreturned candidates would still misattribute a refresh that reoffers the same item under different context. Carry the actual slate/candidate or presentation ID from offer through opening, checkpoint, and submission; record explicit unscheduled/manual provenance for other entry points. Preserve the stronger diagnostic presentation identity already implemented. This retained gap can contaminate both calibration and future training joins without violating a foreign key.

11. **[P2] The retention evaluation counts assisted and confounded follow-ups as retention evidence.** [repositories.py:17201](/home/saturn/Documents/thinking/learnanything/src/learnloop/db/repositories.py:17201), [evaluation.py:348](/home/saturn/Documents/thinking/learnanything/src/learnloop/scheduling/evaluation.py:348). The generic label projector pairs an outcome with up to 20 previous attempts on the learning object. Its raw metadata usefully preserves hints, attempt type, delay, and intervening attempts, but the retention report consumes every same-item pair without applying those eligibility fields or reveal/coldness receipts. A hinted success 40 seconds after the source attempt produced one retention label and one evaluated retention observation. With intervening practice, it also compares the later answer against the source's stability without accounting for the intervening updates. This is retained evaluation behavior, not a defect in the newer cold-outcome ledger. Keep the broad pair records if useful, but define separate versioned eligibility views for descriptive repeated practice, independent next-response prediction, and qualified cold outcomes. Do not feed this report's current aggregate into durable-retention claims or learner-model promotion.

**Performance changes worth doing first**

| Priority | Change | Evidence and expected benefit | Scope |
|---|---|---|---|
| 1 | Reuse one repository connection during short local queue/DTO operations | Existing Repository.pinned reduced the small-fixture queue computation from 59–69 ms to 3.4–3.5 ms; the larger fixture from 37–43 ms to 5.1–5.3 ms | Small; begin with queue building and serialization, then profile feedback and startup |

| 3 | Separate native resource metadata from the RPC mutex; read requested media byte ranges only | serve_llmedia currently reads the entire MP4, then copies the requested slice on every Range request | Small; improves seeking latency and peak allocation for large media |
| 4 | Load large screens on demand | Production build has a 2,126.66 kB main JS chunk, plus a separate 1,255.07 kB PDF worker | Small/medium; start with Reader, graph/knowledge views, and maintenance; measure startup after splitting |
| 5 | Use completion-aware, non-overlapping polling everywhere | The new request hook has recursive timeouts, but Reader guide and exercise-import polling still use intervals around async RPCs | Small; share cancellation/backoff/visibility behavior without hiding feature-specific completion rules |
| 6 | Avoid full startup work on unchanged vault refreshes | SidecarContext.reload invokes load, state sync, canonical projection, and certificate scheduling; successful CLI commands reload even after help/read-only commands | Medium; use operation mutation metadata and versioned projection input fingerprints |

Queue measurements used a fixed clock, persist_explanations=False, identical loaded content, two runs per mode, and disposable copies of migration_head_156 (5 items, 6 attempts) and linear_algebra (99 items, 70 attempts). A follow-up run hashing the complete serialized queue confirmed identical results between pinned and unpinned execution on both fixtures. They measure computation, not total UI latency or durable-write throughput. Counts of repository connection requests were unchanged: 29 and 17 respectively. Connection reuse removes repeated opening/schema work; it is not a substitute for fewer queries. Keep the connection on its owning thread, close it before waiting on AI, and do not turn a performance scope into a long write transaction.

The descriptor experiment demonstrates GC-dependent resource retention, not proof of an indefinitely growing heap under normal GC. SQLite's connection context manager commits/rolls back but does not close the connection, as documented in [Python's sqlite3 guide](https://docs.python.org/3/library/sqlite3.html#how-to-use-the-connection-context-manager). Fix ownership rather than scheduling manual GC. React's [lazy loading API](https://react.dev/reference/react/lazy) can defer screen code until first render; bundle splitting still needs measured startup results before claiming an end-to-end speedup.

Long AI actions should eventually use the existing durable-job pattern with a quick acknowledgement, explicit progress, and cancellation, leaving interactive reads available. Do not solve this by starting an unrestricted new sidecar for every RPC: initialization performs writes, clients carry runtime state, and multiple producers need shared ownership and lease fencing. Likewise, defer a global cache, wholesale async rewrite, or database-engine change until the measured local wins are exhausted.

**Telemetry, dataset readiness, and state.sqlite**

Keep state.sqlite as the local transactional store. Co-locating an attempt, grading evidence, decision references, and durable continuation work makes atomic recording simpler. Moving telemetry to a second database now would introduce another consistency boundary without repairing the incorrect joins above. SQLite explicitly supports desktop application storage; it permits many readers and one writer at a time, which fits short local learning-event writes. See [SQLite's application guidance](https://www.sqlite.org/whentouse.html). The essential architectural distinction is between append-only evidence, immutable decision-time receipts, mutable workflow status, and rebuildable projections, even when all four live in one file.

The repository already has more than generic analytics counters:

| Evidence area | What exists and what it supports | Remaining limit |
|---|---|---|
| Attempts and grading | Answers, hints, priming, latency, rubric/criterion evidence, assessment-contract versions, grading provenance, correction/replay mechanisms | Completion and some secondary writes span multiple commits; a durable attempt alone does not certify all downstream records finished |
| Scheduling | Candidate sets, returned ranks, scores, context/config snapshots, policy versions, selection propensities, attempt links | Findings 9–10 prevent treating these as exact final-offer/behavior-policy records |
| Causal diagnosis | Append-only causal_probe_decision_receipts with inputs, parameters, candidate/hypothesis/repair references; database triggers prevent rewriting/deletion | The current augmentation plan still calls for richer decision-time belief snapshots and complete route-level next/cold outcome and burden joins |
| Cold measurement | Append-only opportunities, opportunity decisions, administration/final coldness receipts, explicit cold_success/cold_failure, right-censoring, refusals and contamination dispositions | Coverage depends on each surface recording delivery/exposure; absence is correctly represented as unknown where the system cannot observe it |
| AI cost | Per-run provider/prompt provenance and estimated/actual token counters; shared finalization captures usage on success and failure | calls/usage-availability are discarded at persistence, so zero conflates no call with unreported usage; process death can leave unfinished runs requiring reconciliation |
| Operational telemetry | Structured RPC/state events, including duration, in the sidecar logger | log_event defaults to DEBUG while normal logging is INFO, and the optional sink is stderr/a debug file, not state.sqlite. This is not an always-on training-data channel |
