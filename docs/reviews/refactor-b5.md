That covers a disabled Decider judgment, no Decider routed, a route that isn't ready, models off, a spend cap, the router's daily guard, a figure-gate refusal, a router ledger refusal and a failed Decider call. ## Records added

All records come from one new module, `src/learnloop/refusal_records.py`. Its builders are pure, and its two writers never raise: `write(repository, kind, build)` joins the repository's open transaction or takes a short one, and `write_on(connection, kind, build)` joins the caller's transaction. The builder runs inside the writer, so a builder that raises is logged with the trace and dropped. The module imports nothing of LearnLoop but the leaf (`learnloop.provenance`). `db.stores.router` writes through it, so importing the store back (`write_decision`) would close an import cycle that the frozen-cycle contract refuses. `write` therefore does `write_decision`'s five lines with the leaf's `provenance.write`. It isn't a second API: same savepoint, same check, same warning.

## The rules from B1 and the strategy

- **A record never changes a decision.** Every builder runs inside a never-raising writer. In `decide` the record's status and rule are worked out inside the builder too. The router guard computes and raises exactly what it did before; only the transaction's end changed, from a rollback of nothing (the guard had only read) to a commit of the record. Tests: a record that can't be built changes no judgment and no refusal, and a whole refused router day serves the same with its records written or dropped.
- **Router paths never wait on the write lock for a record.** The guard's record joins the admission's `BEGIN IMMEDIATE`, which already holds the lock. The follow-up gate's record joins the decision's transaction. The ledger refusal joins the caller's. The Decider judgments and the hint chooser write after their decision, off the router's path.
- **The replay closure.** `decider_judgments` (through AD's replay, `adaptive_difficulty.feature_audit`, which uses the Decider's client and argmax and never `decide`), `db.stores.router` (through `router.outcomes`) and `figure_admission` (through `tutor.tutor_qa`) are in it, so `refusal_records` is too. `test_decision_records_is_unreachable_from_replay` is widened on purpose: `_RECORD_WRITERS` gains `learnloop.refusal_records`, which is set aside from the leaf-use scan like the store. `test_a_rebuild_never_calls_the_record_and_keeps_its_rows` now counts `refusal_records.write` and `write_on` calls during a live rebuild on the head fixture: zero. No other closure module names the table.
- **AD operations.** No writer runs inside an `ad_operation`. AD's feature audit asks the Decider through `adaptive_difficulty.sending`, not through `decide`, and the record writes are in `decide` and `decide_many`, not in `_ask` or `ask_decider`.

## Storage

From the refused arxiv_v2 copy: a `spend_admission` row holds about 300 bytes of JSON (about 0.4 KB with ids and columns), and a `followup_gate` about 0.8 KB (about 1 KB). A refusal record exists only when something refused, so a normal day adds one `followup_gate` per follow-up decision. A day with the daily cap spent adds one row per refused request: 30 on the busiest copy, about 12 KB.
